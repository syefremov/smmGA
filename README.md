# SMM GPT

Система для исследования социальных сетей, подготовки контента, согласования публикаций и анализа результатов. Основной интерфейс — обычный язык в Codex. Дополнительно может быть развёрнута внутренняя веб-панель для календаря, массовой работы, визуального редактора, аналитики и администрирования.

## Статус проекта

Начат репозиторный срез **фазы 7**: версии текстовых знаний, фоновая подготовка индексов,
PostgreSQL FTS, подтверждение владельца, source citations, предложения памяти,
ограниченный AI gateway и экран `/app/knowledge`. Платные вызовы выключены по умолчанию.
**Фаза 7 пока не завершена:** PDF/DOCX upload, hybrid/pgvector, полный набор AI workflows,
реальный корпус/evals и server gates ещё впереди. Точная граница —
[`docs/phase-7-implementation.md`](docs/phase-7-implementation.md).

Добавлен репозиторный срез фазы 6: типизированные источники и факты, планы/брифы/идеи,
неизменяемые редакции, preflight, точное решение владельца и ручной публикационный пакет.
Чат и веб используют одну серверную логику; доступны редактор, материалы и календарь.
В этом срезе ещё нет реальной отправки, ИИ-генерации редакций и загрузки файлов. Scope, тесты и ограничения —
[`docs/phase-6-implementation.md`](docs/phase-6-implementation.md). **Exit gate не закрыт:**
прежние server/identity/two-machine gates и outbox dispatcher остаются незавершёнными.

Добавлен репозиторный срез фазы 5: внутренние задачи в общей БД, одинаковые REST/MCP команды,
справочники и аудит, web shell с личным входом, переносимый plugin и export/doctor прототип.
Серверный запуск и проверка с двух машин **ещё не выполнены**. Реализованные контракты и
проверки — [`docs/phase-5-implementation.md`](docs/phase-5-implementation.md), подключение
сотрудника — [`docs/employee-setup.md`](docs/employee-setup.md). Задачи не являются постами;
публикация и сбор соцсетей пока недоступны.

Добавлен backend foundation фазы 4: персональная web/MCP identity, семь ролей, транзакции, PostgreSQL RLS, аудит и идемпотентные диагностические jobs. Вход пока выключен до настройки реального authentik и private HTTPS. Детали, проверки и незакрытые gates — в [`docs/phase-4-implementation.md`](docs/phase-4-implementation.md); контракты — в [`docs/authentication.md`](docs/authentication.md) и [`docs/data-model.md`](docs/data-model.md).

Исполняемый каркас фазы 2 реализован: FastAPI и Streamable HTTP MCP используют общий сервис состояния, Celery имеет безопасную диагностическую задачу, React-панель получает типы из OpenAPI, а Compose и CI связывают PostgreSQL, Redis, worker, scheduler и reverse proxy. Локальные проверки исходников и полный Linux CI проходят, включая сборку образов, healthy stack, очередь, MCP и Playwright. Exit gate фаз 1–2 пока не закрыт только на текущей Windows-машине: legacy Docker Engine не запускается, и локальный стек должен быть подтверждён после безопасного обновления Docker Desktop. Подробности — в [`docs/phase-2-implementation.md`](docs/phase-2-implementation.md).

Для фазы 3 добавлены отдельный server Compose, двухэтапный bootstrap, deployment/rollback, backup, isolated restore drill, server doctor и Linux CI-сценарий. На удалённом сервере они ещё не применялись: SSH-проверка завершилась таймаутом, recovery-доступ не подтверждён. Порядок запуска — [`docs/deployment.md`](docs/deployment.md), ограничения и эксплуатация — [`docs/operations.md`](docs/operations.md).

Linux CI подтвердил серверный цикл на синтетических данных, включая два releases, повторный deploy, backup/restore и rollback. Результаты и незакрытые пункты фазы 3 — в [`docs/phase-3-implementation.md`](docs/phase-3-implementation.md).

Целевая модель системы зафиксирована в этом документе. При изменении продуктовых или технических решений документ необходимо обновлять вместе с кодом.

## Быстрый локальный запуск

После подготовки рабочей станции:

```text
pnpm bootstrap
pnpm env:init
pnpm check
pnpm test
pnpm dev
```

`pnpm env:init` один раз создаёт игнорируемый Git локальный `.env` со случайными значениями и никогда не перезаписывает существующий файл. `pnpm dev` собирает и запускает весь Compose-контур. После готовности доступны:

- внутренняя status-панель — `http://127.0.0.1:8080/`;
- рабочая панель — `/app/work` (без настроенной личной identity показывает вход, не demo-доступ);
- REST API — `http://127.0.0.1:8080/api/v1/system/status`;
- liveness/readiness — `/health/live` и `/health/ready`;
- MCP Streamable HTTP — `http://127.0.0.1:8080/mcp/`.

Пока Docker Engine недоступен, можно независимо выполнять `pnpm check`, `pnpm test` и `pnpm build:web`. Полная процедура находится в [`docs/local-development.md`](docs/local-development.md).

## Кратко о главном

- Основной интерфейс для владельца и сотрудников — чат Codex; внутренняя веб-панель является дополнительным клиентом того же серверного ядра.
- Правила работы агента хранятся в репозитории, а не только в истории чата.
- Данные хранятся в центральной PostgreSQL на удалённом Linux-сервере.
- PostgreSQL также хранит базу знаний: обычный полнотекстовый индекс и, когда накопятся материалы, embeddings через `pgvector`.
- Codex получает доступ к данным и действиям через удалённый MCP-сервер.
- Веб-панель получает доступ через версионированный HTTPS API; браузер никогда не подключается к PostgreSQL или Redis напрямую.
- Фоновый worker собирает данные, публикует одобренные материалы и снимает метрики по расписанию.
- Сотруднику устанавливается небольшой приватный плагин; база и ключи социальных сетей на его компьютер не копируются.
- Ни один текст нельзя публиковать без зафиксированного одобрения человека.

## Зачем создаётся система

Система должна помогать небольшой команде выполнять полный цикл SMM:

1. Собирать материалы из разрешённых источников.
2. Изучать собственные и выбранные публичные аккаунты.
3. Находить темы, закономерности и идеи для публикаций.
4. Готовить черновики с учётом бренда и площадки.
5. Поддерживать редактирование и согласование.
6. Планировать и публиковать одобренный контент.
7. Сохранять статистику публикаций.
8. Объяснять результаты и предлагать следующие эксперименты.

Система не должна заменять решения человека. Она помогает готовить материалы, выполнять рутинные операции и хранить историю решений.

## Что не входит в продукт

- Публичный маркетинговый сайт и отдельное мобильное приложение; внутренняя защищённая веб-панель допускается.
- Дублирование бизнес-логики отдельно для чата и веб-панели.
- Хранение рабочего состояния только в памяти модели или истории одного чата.
- Автоматическая публикация неподтверждённых черновиков.
- Бесконтрольный парсинг площадок в обход их правил.
- Копирование паролей от базы и социальных сетей на компьютеры сотрудников.
- Полная автономность агента без журнала действий и возможности остановки.
- Микросервисная архитектура до появления реальной необходимости.

## Как пользователь работает с системой

Пользователь пишет обычные команды:

```text
Покажи задачи по контенту на сегодня.
Изучи выбранные Telegram-каналы за последние семь дней.
Предложи десять тем для нашего бренда.
Подготовь третий вариант для Telegram и VK.
Покажи все замечания редактора к посту 42.
Отправь пост 42 на согласование.
Одобри редакцию 7 поста 42.
Запланируй одобренный пост на пятницу, 12:00 по Москве.
Сравни результаты публикаций за август.
Сформулируй три гипотезы для следующей недели.
```

Codex определяет намерение пользователя, показывает понятный ответ и при необходимости вызывает структурированный MCP-инструмент. MCP-сервер повторно проверяет права, входные данные и допустимость перехода состояния. Нельзя полагаться только на правильность интерпретации сообщения моделью.

Если веб-панель включена, сотрудник может открыть тот же проект в браузере: увидеть календарь, сравнить редакции, согласовать материал, просмотреть аналитику или управлять источниками. Действие, выполненное в чате, сразу отражается в веб-панели, и наоборот, потому что оба клиента используют одну базу и одни бизнес-операции.

### Клиенты: Codex и веб-панель

Codex остаётся основным пользовательским интерфейсом. Плагин поставляет:

- SMM-skill с повторяемым рабочим процессом;
- инструкции по формату ответов;
- описание доступных MCP-инструментов;
- адрес удалённого MCP-сервера;
- метаданные установки и обновления.

Плагин не должен содержать общие секреты. Каждый сотрудник проходит отдельную авторизацию и получает только свои права.

Веб-панель — дополнительный внутренний интерфейс для задач, которые удобнее выполнять визуально: календарь, таблицы, редактор, сравнение редакций, просмотр медиа, графики, роли и аудит. Она не содержит отдельной бизнес-логики и использует те же доменные сервисы, проверки прав и переходы состояний, что и MCP.

### Сервер приложения: MCP и Web API

Сервер приложения является единственным контролируемым шлюзом к общей системе. MCP-транспорт обслуживает Codex, а REST/JSON API обслуживает веб-панель. Оба транспорта вызывают одни и те же методы SMM Core и не обращаются к таблицам напрямую в обход бизнес-правил.

Обязанности серверного слоя:

- аутентифицировать пользователя;
- определить его рабочее пространство и роль;
- валидировать параметры;
- вызвать бизнес-операцию SMM Core;
- записать действие в аудит;
- вернуть короткий понятный результат без секретов;
- не выполнять запрещённое действие, даже если агент запросил его ошибочно.

Web API публикуется под `/api/v1`, документируется через OpenAPI и используется для генерации типизированного TypeScript-клиента. Длительные операции возвращают идентификатор фоновой задачи; их прогресс передаётся через Server-Sent Events или опрашивается обычным API. WebSocket добавляется только при появлении сценария, которому действительно нужен двусторонний постоянный канал.

Производственные MCP и Web API работают через стабильный HTTPS-адрес. PostgreSQL и Redis не публикуются в интернет.

### SMM Core

SMM Core содержит всю предметную логику и не зависит от интерфейса чата. Он отвечает за:

- бренды и редакционные правила;
- источники и собранные материалы;
- базу знаний, полнотекстовые индексы и embeddings;
- идеи, посты и редакции;
- согласования;
- расписание публикаций;
- коннекторы социальных сетей;
- метрики, отчёты и эксперименты;
- роли и аудит.

Логика должна быть общей для MCP-инструментов, фоновых задач и будущих служебных CLI-команд.

### PostgreSQL

PostgreSQL — единственный источник истины для рабочего состояния. История чата помогает вести диалог, но не заменяет базу.

В базе хранятся:

- пользователи, роли и рабочие пространства;
- настройки брендов;
- источники и результаты сбора;
- идеи и контент-планы;
- посты и неизменяемые редакции;
- решения о согласовании;
- расписание и попытки публикации;
- снимки метрик;
- история запусков ИИ;
- журнал действий.

### Redis, worker и scheduler

Фоновые процессы не должны зависеть от открытого чата или включённого компьютера сотрудника. Worker выполняет:

- сбор материалов;
- длительный анализ;
- публикацию одобренных постов;
- повтор временно неудавшихся операций;
- сбор метрик;
- подготовку периодических отчётов;
- очистку временных файлов по правилам хранения.

Redis используется как очередь и механизм координации, но не как долговременное хранилище бизнес-данных.

### Коннекторы социальных сетей

Каждая площадка подключается через отдельный адаптер с единым внутренним контрактом:

```text
validate_credentials()
collect_content()
publish_content()
get_publication_status()
collect_metrics()
refresh_credentials()
```

Реальные возможности зависят от официального API конкретной площадки. Если API не предоставляет нужную операцию, система должна честно возвращать ограничение и предлагать ручной импорт или публикацию, а не скрытый обход правил.

## Рекомендуемый технологический стек

Для первой версии используется модульный Python-монолит:

- Python — SMM Core, MCP-сервер и worker;
- официальный Python SDK MCP — протокол инструментов;
- FastAPI — REST API, OpenAPI-контракт, серверные сессии, SSE и health checks;
- SQLAlchemy и Alembic — модели данных и миграции;
- PostgreSQL — постоянные данные;
- встроенный полнотекстовый поиск PostgreSQL — поиск по словам и фразам;
- `pgvector` — смысловой поиск по базе знаний после появления достаточного корпуса;
- Redis и Celery — очередь и фоновые задания;
- защищённый server volume через storage interface — медиа пилота; S3/MinIO подключаются позднее без изменения domain model;
- self-hosted authentik — OIDC и MFA для веб-панели и сотрудников;
- Tailscale Serve — приватный HTTPS-доступ пилота без публичного домена;
- Caddy или Nginx — TLS и reverse proxy;
- Docker Compose — воспроизводимое развёртывание;
- TypeScript, React и Vite — внутренняя одностраничная веб-панель без ненужного SSR;
- TanStack Query — синхронизация серверного состояния, кеширование и обновление данных;
- React Hook Form и Zod — формы и дополнительная клиентская проверка входных данных;
- доступные headless-примитивы компонентов и CSS variables — собственная визуальная система без зависимости бизнес-логики от UI-библиотеки;
- pytest, Ruff и статическая проверка типов — контроль качества Python;
- Vitest, Testing Library, Playwright и автоматические accessibility-проверки — контроль качества веб-панели.

База локальных runtime зафиксирована в `.python-version`, `.node-version`, `package.json` и `scripts/tool-versions.psd1`; Python- и Node-зависимости воспроизводятся через `uv.lock` и `pnpm-lock.yaml`. Обновления выполняются отдельной проверяемой dependency-итерацией.

## Работа с Git

Основная ветка — `main`. По мере начала командной разработки она защищается, а изменения попадают в неё через короткие предметные ветки и pull request. Код, миграции, тесты и связанная документация меняются одним логическим набором.

Агент перед работой проверяет ветку, `git status` и существующие изменения. После каждой законченной и проверенной пользовательской итерации он добавляет только относящиеся к ней файлы, создаёт атомарный commit и отправляет текущую рабочую ветку в настроенный remote. Это постоянное разрешение не распространяется на создание или переключение веток, merge, rebase, force-push, tag, release и deploy.

Секреты и пользовательские данные никогда не добавляются в Git. Lockfiles и согласованные generated-контракты хранятся в репозитории; build output, локальные окружения, кеши, логи, резервные копии и рабочие медиа исключаются. Подробный регламент веток, коммитов, PR, миграций, релизов и восстановления описан в [`docs/git-workflow.md`](docs/git-workflow.md).

## Жизненный цикл публикации

```text
idea
  ↓
draft
  ↓
in_review ───→ rejected ───→ draft
  ↓
approved
  ↓
scheduled
  ↓
publishing
  ↓
published
  ↓
measuring
  ↓
analyzed
```

Дополнительные состояния: `cancelled`, `failed` и `archived`.

Правила переходов:

- редактирование одобренной редакции отменяет её одобрение;
- запланировать можно только конкретную одобренную редакцию;
- публикация сверяет одобрение повторно непосредственно перед отправкой;
- повторная команда не должна создавать второй одинаковый пост;
- отмена расписания не удаляет пост и историю;
- опубликованная версия остаётся неизменной;
- все переходы записываются в аудит.

## Роли и права

| Роль | Возможности |
|---|---|
| Owner | Все permissions; окончательное одобрение конкретной редакции |
| Administrator | Участники, просмотр и аудит; не одобрение/публикация |
| Strategist | Просмотр и планирование |
| Editor | Просмотр и редактирование |
| Publisher | Просмотр и публикация уже одобренного контента |
| Analyst | Просмотр и аналитика |
| Viewer | Только просмотр |

В текущей реализации одна роль на membership; Owner имеет все permissions. Owner/Administrator/Publisher требуют MFA. Подробная исполняемая матрица и граница между permissions и уже готовыми операциями описаны в [`docs/authentication.md`](docs/authentication.md). Совмещение ролей и делегирование одобрения — отдельное будущее изменение, не разрешение по умолчанию.

## Специализированные AI-профили

Человеческие роли определяют права сотрудников, а AI-профили — узкую функцию конкретного запуска. Эти понятия нельзя смешивать: название AI-профиля не даёт ему разрешений пользователя или администратора.

Из руководства GreenAurum адаптируется полезное разделение труда:

| AI-профиль | Результат в нашей системе |
|---|---|
| Research Scout | Проверенные находки, источники, уровень уверенности и идеи применения |
| Analyst | Отчёты, сопоставимые метрики, ограничения данных и гипотезы |
| Content Planner | Контент-план, рубрики, слоты, briefs и зависимости |
| Product Expert | Версионированные продуктовые факты, FAQ, ограничения и пробелы знаний |
| Copywriter | Новая редакция поста на основании brief и разрешённых источников |
| Visual Creator | Варианты визуала с provenance, параметрами генерации и привязкой к редакции |
| Editor / Compliance Reviewer | Структурированные findings и рекомендация, но не человеческое одобрение |
| Publisher | Проверка комплекта и выполнение только уже разрешённой публикации |
| Community Manager | Черновики ответов, темы из повторяющихся вопросов и эскалации |
| Orchestrator | Декомпозиция кампании, зависимости, статусы и блокеры без выполнения работы специалистов |

В MVP это не десять постоянно работающих процессов и не десять независимых «личностей». Это версионируемые серверные профили, запускаемые по необходимости одним оркестратором или пользователем. Такое устройство сохраняет специализацию, но не создаёт лишнюю инфраструктуру и отдельную неконтролируемую память.

Каждый профиль имеет явные входы, структурированный выход, разрешённые инструменты, запрещённые действия, критерии качества и путь эскалации. Права ограничиваются механизмами сервера: например, Copywriter технически не может публиковать, а Orchestrator не может подменить Editor. Постоянное наблюдение агента попадает сначала в `memory_proposals`; рабочим правилом оно становится только после проверки человека.

Markdown-vault и Hermes-конфигурации из исходного руководства не переносятся как источник истины. Документы можно импортировать, экспортировать или просматривать в Markdown, но состояние, версии, связи и аудит остаются в PostgreSQL. Подробная адаптация, конвейеры и порядок внедрения описаны в [`docs/agent-workflows.md`](docs/agent-workflows.md).

## Исследование социальных сетей

Каждый собранный материал должен иметь:

- источник и внешний URL или идентификатор;
- дату публикации и дату получения;
- автора или аккаунт, если он доступен;
- исходный текст или разрешённый фрагмент;
- тип получения: API, RSS, импорт или ручной ввод;
- технический статус и возможные ограничения качества.

Выводы ИИ должны отличать факты от предположений. При подготовке идеи необходимо сохранять ссылки на использованные `source_items`, чтобы пользователь мог проверить происхождение тезиса.

Основной путь интеграции — официальные API. Автоматизированный браузер или парсинг используются только после проверки правил площадки и явного решения владельца проекта.

## Подготовка контента

Перед генерацией система собирает контекст:

- профиль бренда;
- целевую аудиторию;
- цель публикации;
- выбранную площадку;
- ограничения формата;
- исходные материалы;
- релевантные предыдущие публикации;
- активный эксперимент, если он есть.

Результат должен включать не только текст:

- тему и цель;
- основную редакцию;
- варианты заголовка или первого абзаца;
- призыв к действию, если он уместен;
- предложение по медиа;
- источники проверяемых утверждений;
- предупреждения о неподтверждённых фактах;
- адаптации для выбранных площадок.

## База знаний и RAG

RAG нужен для поиска внутреннего контекста перед генерацией, а не для хранения рабочего состояния. Например, при создании поста система может подобрать действующий tone of voice, описание продукта, подходящие материалы исследования и несколько ранее одобренных публикаций.

Для первой версии отдельная векторная база не используется. Система начинает с PostgreSQL и обычного полнотекстового поиска. После появления полезного корпуса подключается расширение `pgvector`, и поиск становится гибридным:

1. Сервер определяет пользователя, `workspace_id`, бренд и его права.
2. SQL-фильтры исключают чужие, архивные, просроченные и недоступные документы.
3. Полнотекстовый поиск находит точные названия, термины и фразы.
4. Векторный поиск находит близкие по смыслу фрагменты.
5. Результаты объединяются, устраняются дубликаты и ранжируются.
6. Модели передаётся только небольшой набор лучших фрагментов вместе с идентификаторами источников.
7. Ответ отделяет найденные факты от предложений ИИ и показывает происхождение проверяемых утверждений.

В базу знаний включаются:

- правила бренда и примеры стиля;
- описания продуктов, услуг и ограничений;
- FAQ и утверждённые ответы клиентам;
- разрешённые исследовательские материалы;
- ранее одобренные публикации;
- подтверждённые выводы аналитики.

В неё не включаются секреты, пароли, токены, полные резервные копии, произвольная история чатов и данные другого рабочего пространства. Актуальные метрики, состояния публикаций и права всегда запрашиваются из нормализованных таблиц.

Каждый найденный фрагмент обязан сохранять происхождение: документ, версия, источник, дата получения, область доступа и связь с исходной записью. Если источник устарел, противоречит другому документу или не подтверждает тезис, система сообщает об этом, а не маскирует неопределённость.

Embeddings создаются через внутренний интерфейс-провайдер. В БД записываются модель, размерность, версия разбиения и хеш исходного текста. Смена модели не должна незаметно смешивать несовместимые векторы: новая версия строится фоновой задачей и переключается только после проверки.

Подробный контракт индексации, поиска, безопасности и оценки качества описан в [`docs/knowledge-rag.md`](docs/knowledge-rag.md).

## Согласование и защита от случайной публикации

Команда «хорошо», «нормально» или аналогичная реакция не считается разрешением на публикацию, если из контекста не следует однозначное одобрение конкретной редакции.

Надёжный процесс:

1. Codex показывает номер поста, номер редакции и полный текст.
2. Пользователь явно одобряет эту редакцию.
3. MCP-сервер сохраняет отдельную запись `approvals`.
4. При планировании сохраняется идентификатор одобренной редакции.
5. Worker перед публикацией повторно проверяет состояние, права и редакцию.
6. После успешной публикации сохраняется внешний идентификатор.

Для защиты от дублей используется идемпотентный ключ. Неопределённый результат отправки сначала проверяется через API площадки и не повторяется вслепую.

## Аналитика

Метрики хранятся снимками, потому что значения меняются со временем. Рекомендуемые точки наблюдения задаются отдельно для каждой площадки, например через несколько часов, сутки, трое и семь суток после публикации.

Система анализирует:

- просмотры и охват;
- реакции и комментарии;
- сохранения и репосты, если доступны;
- клики и переходы;
- прирост аудитории;
- абсолютные значения и нормализованные коэффициенты;
- тему, формат, время, длину и экспериментальную гипотезу.

ИИ формулирует выводы как объяснимые гипотезы. Корреляция не должна представляться доказанной причинностью. Отчёт обязан указывать период, размер выборки, отсутствующие данные и использованную формулу.

## Внутренняя веб-панель

Веб-панель дополняет чат, но не заменяет его и не создаёт вторую систему. Она особенно полезна там, где естественный язык менее удобен, чем визуальное представление:

- календарь и очередь публикаций;
- табличная фильтрация большого числа материалов;
- редактор текста и медиа с предпросмотром площадки;
- сравнение редакций и согласование;
- просмотр источников и базы знаний;
- графики метрик и сравнение экспериментов;
- управление командой, интеграциями и аудитом.

Все изменения проходят через серверный API и те же доменные операции, что используются MCP-инструментами. Интерфейс может скрывать недоступную кнопку, но окончательное решение о праве всегда принимает сервер. Опасные операции не выполняются оптимистически: перед публикацией показываются точная редакция, площадка, аккаунт и время, а сервер повторно проверяет одобрение и конкурентные изменения.

Веб-панель проектируется как спокойное рабочее пространство, а не как набор декоративных dashboard-карточек. Основная компоновка: навигация, центральная рабочая область и контекстный инспектор. На мобильном устройстве обязательны просмотр, комментарии, согласование и экстренная отмена расписания; сложное массовое редактирование может оставаться desktop-first.

Подробные маршруты, UX-состояния, frontend-стек, API, авторизация, безопасность, доступность, тестирование и развёртывание описаны в [`docs/web-app.md`](docs/web-app.md).

## Перенос на компьютер сотрудника

Сотруднику не передаётся серверная часть. Для работы через чат он получает приватный плагин и при необходимости репозиторий с проектными инструкциями. Для работы через веб-панель достаточно современного браузера и персональной учётной записи.

Планируемый процесс установки:

1. Установить Codex и войти в разрешённую рабочую область.
2. Установить Tailscale и войти в приглашённую организацию пилота.
3. Скачать приватный пакет или клонировать закрытый репозиторий.
4. Запустить `scripts/install-smm.ps1`.
5. Установить SMM-плагин.
6. Авторизоваться на центральном MCP-сервере.
7. Выполнить тестовую команду `Покажи доступные рабочие пространства`.

Установщик не должен просить пароль PostgreSQL или ключи социальных сетей. Авторизация сотрудника выполняется отдельно, а его доступ можно отозвать на сервере.

История чатов сотрудников может отличаться. Общее состояние остаётся единым, поскольку хранится в PostgreSQL.

Веб-доступ упрощает подключение временного сотрудника: установка проекта не требуется, а отзыв серверной сессии немедленно прекращает доступ. Плагин и браузер могут использоваться одним человеком параллельно.

## Удалённый Linux-сервер

Серверная раскладка фазы 3:

```text
/opt/smm-gpt/          # immutable releases и metadata последнего успешного deploy
/etc/smm-gpt/          # root-only configuration/secrets
/var/lib/smm-gpt/      # постоянные данные, media и isolated restore drills
/var/backups/smm-gpt/  # локальные staging-копии; не offsite backup
```

Локальный `compose.yaml` уже содержит сервисы фазы 2:

- `app` — MCP и REST API;
- `web` — Caddy раздаёт собранную SPA и проксирует API/MCP;
- `migrate` — одноразово применяет Alembic migrations до запуска приложения;
- `worker`;
- `scheduler`;
- `postgres` — source of truth с host-портом только на `127.0.0.1`;
- `redis` — очередь и временная координация с host-портом только на `127.0.0.1`.

Server manifest `ops/compose.server.yaml` не наследует локальные port mappings: только Caddy опубликован на `127.0.0.1:8080`. Tailscale Serve включается оператором после проверки ACL и направляется на Caddy. Пока нет identity фазы 4, сервер отдаёт только синтетическую страницу состояния/health; remote MCP и прочие API закрыты кодом 403. authentik и объектное хранилище пока не развёрнуты. Серверные команды описаны в [`docs/deployment.md`](docs/deployment.md).

В production предпочтителен один внешний origin: reverse proxy раздаёт веб-панель, направляет `/api/*` в FastAPI и публикует MCP на отдельном защищённом пути или поддомене. Это упрощает cookie, CORS и защиту от CSRF. Frontend может собираться отдельным контейнером, но готовые статические файлы раздаются proxy без постоянно работающего Node.js-процесса.

Для пилота без собственного домена сервер доступен только внутри приватной Tailscale-сети через HTTPS-имя `*.ts.net`; Tailscale Funnel не включается. Название узла выбирается без названия клиента или другой чувствительной информации, поскольку имя сертификата может появляться в публичных certificate transparency logs. После появления корпоративного домена reverse proxy переключается на `smm.<домен-компании>`, а внутренние API-контракты не меняются.

В пилоте веб-панель и MCP не открываются в публичный интернет: доступ идёт через Tailscale. Публично остаются только действительно необходимые серверные порты, а SSH дополнительно ограничивается ключами и firewall. PostgreSQL, Redis и внутренние сервисы доступны только сети контейнеров или приватной сети. Развёртывание не должно выполняться от `root` постоянно: после начальной настройки создаётся отдельный системный пользователь с минимальными правами.

## Конфигурация и секреты

В Git можно хранить:

- `.env.example` без значений;
- имена переменных;
- безопасные значения по умолчанию;
- публичные адреса и документацию;
- схемы и миграции.

В Git нельзя хранить:

- пароли;
- приватные SSH-ключи;
- токены социальных сетей;
- ключи API;
- cookie и сессии браузера;
- резервные копии с реальными данными;
- строки подключения с учётными данными.

Секреты хранятся на сервере в защищённом окружении или специализированном хранилище. В логах, ответах MCP и сообщениях чата они маскируются.

## Надёжность

- Все даты в базе хранятся в UTC; пользовательский часовой пояс хранится отдельно.
- Запланированные действия блокируются от параллельного двойного выполнения.
- Внешние операции имеют идемпотентные ключи.
- Временные ошибки повторяются с ограничением и увеличивающейся задержкой.
- Постоянные ошибки переводят задачу в `failed` и требуют внимания.
- Неопределённый результат публикации проверяется перед повтором.
- Миграции базы обратимы, когда это практически возможно.
- Резервные копии создаются автоматически и периодически проверяются восстановлением.

## Наблюдаемость и аудит

Для каждого действия сохраняются:

- время;
- пользователь или системная задача;
- рабочее пространство;
- тип операции;
- идентификаторы затронутых объектов;
- итоговый статус;
- безопасное описание ошибки;
- идентификатор корреляции для поиска по журналам.

Нельзя записывать в аудит токены, пароли или полный заголовок авторизации. Пользовательские отчёты должны быть понятными, а технические журналы — достаточными для диагностики.

## Тестирование

Минимальная стратегия:

- unit-тесты бизнес-правил и переходов состояний;
- интеграционные тесты PostgreSQL и очереди;
- контрактные тесты MCP-инструментов;
- тестовые адаптеры социальных сетей без реальной публикации;
- сценарий публикации в песочнице или тестовом аккаунте;
- проверка идемпотентности и повторов;
- проверка разграничения рабочих пространств;
- проверка, что RAG никогда не возвращает материалы чужого рабочего пространства или более высокого уровня доступа;
- проверка полнотекстового, смыслового и гибридного поиска на фиксированном тестовом наборе;
- проверка ссылок на источники, обработки устаревших документов и повторной индексации;
- проверка, что изменение редакции отменяет одобрение;
- unit-тесты frontend-компонентов, форм и разрешений на отображение действий;
- browser-тесты критических путей: вход, создание черновика, сравнение, согласование, планирование и отмена;
- проверка клавиатурной навигации, фокуса, контраста и основных критериев WCAG 2.2 AA;
- проверка истечения и отзыва веб-сессии, CSRF, загрузки файлов и обработки конфликтов версий;
- проверка резервного копирования и восстановления перед production.

Реальные публикации и платные внешние вызовы не запускаются в обычном наборе тестов.

## Этапы реализации

Полная реализация разделена на десять последовательных фаз:

| Фаза | Содержание | Итог |
|---:|---|---|
| 1 | Windows-машина, версии и bootstrap | Воспроизводимая среда разработчика |
| 2 | Monorepo, локальный Compose и CI | Исполняемый технический каркас |
| 3 | Linux-сервер, SSH, firewall и Tailscale | Приватный серверный staging |
| 4 | PostgreSQL, identity, роли и аудит | Безопасный многопользовательский фундамент |
| 5 | Domain gateway, MCP, REST, plugin и web shell | Удалённый chat-first alpha |
| 6 | Контент, revisions, review, approval и календарь | Полезный MVP без реальной автопубликации |
| 7 | Knowledge pipeline, hybrid RAG и AI-профили | Source-grounded AI beta |
| 8 | VK, worker/scheduler, WB import и community intake | Контролируемый интеграционный пилот |
| 9 | Полный web UX, аналитика, Orchestrator и employee installer | Командный release candidate |
| 10 | Security, monitoring, backup/restore, rollback и UAT | Production-ready пилот |

В каждой фазе определены работы, артефакты, проверки и обязательный exit gate. Фаза не считается завершённой только потому, что код написан: должны пройти воспроизводимый запуск, тесты, проверка секретов и сценарий восстановления. Полный план, включая точные зависимости локальной машины и сервера, находится в [`docs/roadmap.md`](docs/roadmap.md).

Текущий статус: репозиторная реализация фаз 2–3 подготовлена; локальные gates фаз 1–2 и реальная серверная приёмка фазы 3 ещё не закрыты. Команды `dev`, `test`, `build` и `db:migrate` реализованы; Compose-зависимые команды требуют рабочего Docker Engine. Диагностика Windows — `pnpm run doctor`; серверные процедуры — [`docs/deployment.md`](docs/deployment.md).

Отдельная векторная БД, reranker или дополнительный поисковый сервис добавляются только тогда, когда измерения покажут, что PostgreSQL не обеспечивает требуемые объём, задержку или качество. Orchestrator включается последним, после стабильной работы специализированных профилей и их quality gates.

## Критерии готовности MVP

Первая полезная chat-first версия считается готовой, когда:

- пользователь управляет системой только из чата;
- данные сохраняются между чатами и компьютерами;
- доступны профиль бренда, источники, идеи, посты и редакции;
- продуктовые факты имеют источник, версию и явные пробелы вместо догадок;
- автоматический preflight возвращает структурированные замечания и не подменяет одобрение человека;
- полнотекстовый поиск по разрешённым материалам работает с изоляцией рабочих пространств;
- согласование относится к конкретной редакции;
- нельзя опубликовать неутверждённый текст;
- подключена одна реальная площадка;
- публикация защищена от дублей;
- метрики хотя бы одной площадки сохраняются снимками;
- сотрудник устанавливает пакет по документированной процедуре;
- его доступ можно отозвать без смены всех общих секретов;
- сервер восстанавливается из проверенной резервной копии.

Веб-панель считается готовой к включению отдельно, когда она использует те же права и переходы состояний, покрывает основные сценарии сотрудника, не хранит токены в `localStorage`, корректно работает с клавиатуры и на мобильном экране, а её критические пути проходят автоматические browser-тесты. Поэтому разработка веб-панели не блокирует раннюю полезную версию чата.

## Принятые решения для пилота

Чтобы не останавливать разработку на продуктовых вопросах, для первой версии приняты обратимые defaults:

| Вопрос | Решение |
|---|---|
| Первый workspace | GreenAurum |
| Первая социальная сеть | ВКонтакте; интеграция только через официальный разрешённый способ |
| Связанные продажи | Wildberries через ручной импорт разрешённых выгрузок, затем официальный API при наличии доступа |
| Окончательное одобрение | Owner workspace; делегирование потребует отдельного permission design |
| Публикация | Сначала package/manual и dry-run, затем connector; каждый реальный пост подтверждается отдельно |
| Доступ без домена | Приватный Tailscale + HTTPS/MagicDNS; публичный Funnel отключён |
| Production-адрес | Позже отдельный `smm.<домен-компании>` без изменения приложения |
| Вход | Self-hosted authentik по OIDC; MFA обязательно для Администратора и Публикатора |
| Медиа | Защищённый серверный volume через storage interface; S3/MinIO только при появлении необходимости |
| Главные метрики | Охват/просмотры, engagement rate by reach, переходы на WB и подтверждённые продажи/промокоды при наличии данных |
| Источники знаний | Утверждённые product facts, brand voice, claim policies, FAQ, verified research и approved posts |
| Владельцы знаний | Владелец workspace утверждает; Product Expert/Editor предлагают изменения |
| Mobile | Просмотр, комментарий, approve/reject, статусы и экстренная отмена расписания |
| Community | Сначала ручной импорт текста/CSV и только черновики ответов |
| Отзывы и UGC | Не используются в контенте без отдельной записи согласия, scope и возможности отзыва |

Полный журнал решений, последствия и условия пересмотра находится в [`docs/decisions.md`](docs/decisions.md). Эти defaults можно менять позже через документированное решение и миграцию, а не случайной правкой поведения.

## Что потребуется от владельца системы

Большую часть технической работы — каркас проекта, миграции, MCP-инструменты, тесты, Docker Compose, развёртывание и установщик — можно выполнять последовательно без дополнительных продуктовых вопросов. От владельца понадобятся только реальные материалы, внешние доступы и подтверждения, которые нельзя корректно придумать или выдать автоматически:

- предоставить реальные материалы GreenAurum и указать, какие из них действующие;
- предоставить список первых сотрудников, когда начнётся многопользовательский тест;
- оформить доступ к официальному API ВКонтакте, когда дойдём до connector;
- предоставить разрешённые выгрузки Wildberries для аналитики;
- вводить рабочие секреты непосредственно в защищённое серверное окружение, а не сохранять их в Git или документации;
- подтвердить тестовую публикацию перед любым внешним действием.

Каждый следующий этап должен завершаться проверяемым результатом и короткой инструкцией восстановления. Разработка не должна перескакивать к автоматической публикации или сложному RAG до прохождения базовых проверок данных, прав и согласования.

## Почему используются AGENTS.md, skill, plugin, MCP и Web API

- Plugin является устанавливаемой единицей для компьютеров сотрудников.
- MCP подключает чат к общей базе, фоновым задачам и внешним сервисам.
- Web API подключает внутреннюю браузерную панель к тем же доменным операциям без дублирования логики.

Такое разделение соответствует рекомендациям OpenAI по настройке Codex: [AGENTS.md и инструкции проекта](https://learn.chatgpt.com/docs/agent-configuration/agents-md) и [обзор AGENTS, skills, plugins и MCP](https://learn.chatgpt.com/docs/customization/overview).
