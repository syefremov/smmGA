# Git-регламент проекта

Этот документ определяет, как люди и агенты работают с Git в SMM GPT. Цель — сохранять понятную историю, не терять чужие изменения, не допускать секреты в репозиторий и отделять изменение кода от production-развёртывания.

## 1. Базовые правила

1. Основная ветка называется `main` и должна оставаться работоспособной.
2. PostgreSQL, сервер и рабочие компьютеры не являются заменой Git-репозитория.
3. Git хранит код, миграции, документацию, тесты и воспроизводимую конфигурацию без секретов.
4. Пользовательские документы, публикации, метрики, загруженные медиа и резервные копии хранятся вне Git.
5. Commit или merge не является разрешением на deploy.
6. Владелец дал постоянное разрешение после каждой завершённой и проверенной итерации создавать атомарный commit относящихся к ней изменений и отправлять текущую рабочую ветку в настроенный remote.
7. Одна итерация — один пользовательский запрос или один согласованный логический результат. Частичные или неработающие состояния не коммитятся как шумные checkpoints, если пользователь отдельно этого не попросил.
8. Постоянное разрешение не включает создание или переключение веток, amend, rebase, merge, force-push, tag, release или deploy.
9. Любые уже существующие изменения считаются принадлежащими пользователю и не включаются автоматически.

## 2. Перед началом работы

Минимальная read-only проверка:

```text
git status --short --branch
git diff --stat
git diff
git log -5 --oneline --decorate
```

При необходимости дополнительно проверяются staged diff, текущий remote и расхождение с upstream. Получение сведений о remote не даёт разрешения изменять файлы или историю.

Если рабочее дерево содержит изменения:

- определить, относятся ли они к задаче;
- не удалять и не откатывать их;
- не выполнять автоматический stash;
- не включать посторонние файлы в будущий commit;
- при пересечении строк аккуратно сохранить оба намерения или остановиться и описать конфликт.

Нельзя добиваться «чистого состояния» ценой потери пользовательской работы.

## 3. Ветки

### Основная ветка

`main` содержит интегрированное состояние и должна проходить обязательные проверки. После появления нескольких разработчиков или production-окружения для неё включается branch protection.

Рекомендуемые требования защиты:

- pull request перед merge;
- успешный CI;
- отсутствие unresolved conversations;
- запрет force push;
- запрет удаления ветки;
- обязательный review для auth, permissions, publishing, migrations и production infrastructure;
- актуальность ветки относительно `main`, когда это необходимо для безопасного merge.

### Рабочие ветки

Формат:

```text
feature/<short-name>
fix/<short-name>
docs/<short-name>
chore/<short-name>
release/<version>
```

Примеры:

```text
feature/post-approval
fix/publication-idempotency
docs/web-auth-flow
chore/update-python-tooling
```

Имена используются на английском, в нижнем регистре, слова разделяются дефисами. Ветка должна решать одну понятную задачу и жить недолго.

Постоянная ветка `develop` не создаётся без отдельного архитектурного решения. Для раннего одиночного прототипа допустима работа в `main`, но перед командной или production-работой следует перейти к защищённой `main` и pull requests.

### Переключение и создание веток

Агент не создаёт и не переключает ветку самостоятельно, если пользователь не попросил. Автоматический commit/push выполняется в текущую рабочую ветку. Перед разрешённым переключением проверяется, что операция не затронет незакоммиченные изменения.

## 4. Коммиты

### Формат сообщения

Используется Conventional Commits:

```text
type(scope): imperative summary
```

Допустимые основные типы:

- `feat` — пользовательская возможность;
- `fix` — исправление дефекта;
- `docs` — только документация;
- `test` — тесты без изменения поведения;
- `refactor` — изменение внутренней структуры без новой функции;
- `perf` — измеримое улучшение производительности;
- `build` — сборка и зависимости;
- `ci` — автоматизация проверок и релизов;
- `chore` — служебное изменение;
- `revert` — явный откат commit.

Рекомендуемые scopes:

```text
core auth api mcp web knowledge content approvals publishing analytics infra docs
```

Примеры:

```text
feat(approvals): require an immutable revision
fix(publishing): prevent duplicate Telegram delivery
docs(web): define session and CSRF rules
test(auth): cover cross-workspace access denial
```

Заголовок пишется на английском в повелительной форме, без точки в конце. Тело может быть на русском, если так яснее описывается бизнес-контекст, риск или миграция.

### Содержимое commit

Commit должен быть атомарным:

- включать одну логическую причину изменения;
- содержать соответствующие тесты;
- содержать миграцию при изменении схемы;
- обновлять документацию при изменении контракта или поведения;
- не смешивать механическое форматирование с предметным изменением без необходимости;
- не включать временные файлы и посторонние пользовательские изменения.

Перед commit проверяются:

```text
git status --short
git diff
git diff --staged
```

Файлы добавляются в staging явными путями. `git add .` или `git add -A` не используются вслепую в загрязнённом рабочем дереве.

Commit создаётся после успешных релевантных проверок, проверки секретов и просмотра staged diff. Затем текущая ветка отправляется в её настроенный upstream. Если проверки или push недоступны, агент не маскирует проблему: сохраняет безопасное локальное состояние и сообщает точный блокер.

### Исправление commit

`git commit --amend` допускается только для собственного последнего непубличного commit и только по явной команде. Чужие или уже отправленные commits не переписываются без координации.

## 5. Запрещённые и опасные операции

Без отдельного точного разрешения нельзя выполнять:

- `git reset --hard`;
- `git clean -fd` или более широкие варианты;
- восстановление файлов через checkout/restore с потерей изменений;
- interactive rebase опубликованной истории;
- `git push --force`;
- удаление remote-веток или tags;
- массовую очистку untracked-файлов;
- автоматический stash пользовательских изменений;
- удаление `.git` или повторную инициализацию поверх репозитория.

Даже при разрешённой переписи истории используется `--force-with-lease`, а точная ветка и последствия проверяются заранее.

## 6. Pull request

Pull request должен объяснять результат, а не перечислять файлы.

Минимальное содержание:

- что изменилось и зачем;
- границы задачи и что не менялось;
- как проверить результат;
- выполненные тесты;
- риски и ограничения;
- миграции данных;
- порядок deploy и rollback, если применимо;
- скриншоты или короткая запись для заметных frontend-изменений;
- влияние на permissions, секреты, внешние API и публикацию.

Автор выполняет self-review diff до запроса review. Временный debug-код, закомментированные секреты, случайное форматирование и непонятные generated changes удаляются.

### Обязательный review

Отдельное внимание требуется для:

- аутентификации и сессий;
- ролей и изоляции workspace;
- публикации и идемпотентности;
- интеграционных credentials;
- SQL-миграций;
- RAG-фильтрации и доступа к документам;
- загрузки файлов;
- Docker, reverse proxy, CI и deploy;
- удаления или изменения политики хранения данных.

### Стратегия merge

По умолчанию используется squash merge для коротких рабочих веток. Итоговое сообщение соответствует Conventional Commits и описывает полезный результат.

Merge commit допустим для release-веток или осознанного сохранения структуры серии commits. Стратегия не меняется от PR к PR без причины.

## 7. Синхронизация и конфликты

Перед интеграцией рабочая ветка синхронизируется с актуальной `main`. Rebase подходит для собственной неопубликованной или согласованной ветки; merge предпочтительнее, если ветку уже совместно используют и переписывать её нельзя.

При конфликте:

1. понять смысл обеих сторон;
2. не выбирать автоматически только «нашу» или «их» версию;
3. проверить связанные тесты и документацию;
4. показать неожиданный предметный конфликт пользователю;
5. после разрешения заново выполнить проверки.

Нельзя разрешать конфликт в миграциях простой заменой номера или удалением одной миграции. Сначала проверяется фактический граф миграций.

## 8. Секреты и чувствительные данные

В Git запрещены:

- пароли и API keys;
- access/refresh tokens;
- приватные SSH-ключи;
- cookies и session identifiers;
- реальные `.env`;
- connection strings с credentials;
- database dumps;
- production-логи с пользовательскими данными;
- реальные документы клиентов и выгрузки соцсетей;
- object-storage credentials и подписанные URL с длительным сроком.

`.gitignore` снижает вероятность случайной ошибки, но не является защитой. Перед commit выполняется просмотр diff и, после настройки CI, secret scan.

Если секрет попал в commit:

1. прекратить дальнейшее распространение;
2. немедленно отозвать или заменить секрет;
3. определить, был ли commit отправлен в remote;
4. согласовать очистку истории;
5. не считать удаление строки из нового commit достаточным;
6. зафиксировать безопасное описание инцидента без самого секрета.

Перепись опубликованной истории выполняется только как отдельная согласованная операция.

## 9. `.gitignore` и локальные файлы

В репозитории не хранятся:

- Python virtual environments и caches;
- `node_modules` и frontend build output;
- coverage и browser-test reports;
- IDE/OS metadata;
- runtime logs и PID;
- локальные volumes, dumps и backups;
- реальные `.env`;
- локальный каталог `output/`.

Шаблоны `.env.example` хранят только названия переменных и безопасные placeholders. Они не должны содержать значения, похожие на реальные credentials.

## 10. Переносы строк и бинарные файлы

`.gitattributes` фиксирует LF для кода, документации и конфигурации. `.cmd` и `.bat` используют CRLF. Медиа, документы, архивы и шрифты обозначаются binary, чтобы Git не пытался выполнять текстовое сравнение или менять переносы строк.

После первого добавления `.gitattributes` массовая нормализация существующих файлов выполняется отдельным commit. Она не смешивается с функциональной разработкой.

## 11. Большие файлы и Git LFS

Пользовательские изображения, видео и выгрузки должны попадать в S3-совместимое хранилище, а не в Git.

В Git допустимы небольшие стабильные design assets, fixtures и документационные примеры без чувствительных данных. Если действительно нужен большой версионируемый бинарный asset, Git LFS подключается отдельным решением до первого commit этого файла.

Нельзя сначала закоммитить большой бинарный файл, а потом просто добавить LFS: исходный blob останется в истории. Миграция существующей истории требует отдельного согласования.

## 12. Зависимости и lockfiles

В Git хранятся:

- Python project metadata и выбранный lockfile;
- `package.json`;
- frontend lockfile;
- точная версия package manager;
- Docker image versions или digests;
- migration files.

Обновление зависимостей выполняется отдельным понятным изменением. В PR указываются существенные breaking changes, новая лицензия, security impact и результат тестов.

Несколько конкурирующих lockfiles для одного проекта не допускаются.

## 13. Generated-файлы

Источник генерации всегда определён явно.

Типизированный frontend API client генерируется из OpenAPI backend-приложения. Сгенерированный client хранится в Git, чтобы:

- diff API был виден при review;
- frontend собирался воспроизводимо;
- рассинхронизация обнаруживалась CI.

Изменение generated client без изменения источника или команды генерации считается ошибкой. CI заново генерирует файлы и проверяет отсутствие diff.

Build artifacts, coverage, временные exports и скомпилированные frontend assets в Git не хранятся.

## 14. Миграции базы данных

Каждое изменение схемы имеет новую Alembic migration. Уже применённая или отправленная в общую ветку migration не редактируется; исправление создаётся следующей migration.

Правила:

- модель и migration входят в один PR;
- upgrade проверяется на новой и реалистичной существующей базе;
- downgrade реализуется, когда он безопасен и честен;
- необратимость описывается явно;
- большие изменения данных отделяются от блокирующей schema migration;
- production-совместимость строится по expand/migrate/contract;
- удаление колонок происходит только после прекращения их использования приложением;
- backup и rollback определяются до опасного изменения.

Merge migration не означает автоматическое применение к production.

## 15. Тесты и CI

Минимальные CI-проверки по мере появления кода:

- форматирование и lint Python;
- type checking Python;
- unit и integration tests;
- проверка Alembic migration graph;
- frontend formatting и lint;
- TypeScript typecheck;
- frontend unit/component tests;
- OpenAPI regeneration diff;
- production frontend build;
- критические Playwright scenarios;
- secret scan;
- dependency/security scan;
- проверка Docker Compose configuration;
- проверка Markdown links и базового форматирования документации.

Required checks должны иметь стабильные имена. Их нельзя обходить через `--no-verify`, отключение workflow или подмену теста пустой проверкой.

Flaky test сначала диагностируется. Его временное отключение требует issue/описания причины, владельца и условия возврата.

## 16. Версии и релизы

После появления deployable продукта используется Semantic Versioning:

- `MAJOR` — несовместимые изменения внешнего контракта или процесса обновления;
- `MINOR` — обратно совместимые возможности;
- `PATCH` — обратно совместимые исправления.

Tag имеет вид `vX.Y.Z` и создаётся только на проверенном commit. Production artifacts маркируются tag и полным commit SHA. Пересоздание другого содержимого под существующим tag запрещено.

Release notes включают:

- пользовательские изменения;
- миграции и требования обновления;
- исправления безопасности без раскрытия уязвимых секретов;
- известные ограничения;
- порядок отката.

## 17. Deploy и rollback

Git-операции и эксплуатационные действия разделены:

```text
commit → pull request → CI → merge → release/tag → explicit deploy
```

Push в `main` не должен случайно публиковать посты, менять credentials или применять необратимую production migration без контролируемого release-процесса.

Перед production deploy фиксируются:

- точный SHA/tag;
- backup status;
- список migrations;
- совместимость старого и нового приложения;
- health checks;
- критерии остановки;
- rollback procedure.

Rollback кода не всегда откатывает данные. Для каждой опасной migration это оценивается отдельно.

## 18. Hotfix

Hotfix создаётся от актуальной production-версии или `main`, если они совпадают. Он содержит минимальное исправление и тест воспроизведения. Обычные требования review и CI сохраняются настолько, насколько позволяет срочность.

После выпуска исправление должно присутствовать во всех активных ветках. Срочность не разрешает помещать секреты в Git, обходить аудит публикации или использовать разрушительные команды без проверки.

## 19. Действия агента при завершении задачи

Перед передачей результата агент:

1. повторно проверяет `git status --short --branch`;
2. просматривает diff только относящихся к задаче файлов;
3. запускает доступные релевантные проверки;
4. проверяет, что не появились секреты и большие случайные файлы;
5. сообщает изменённые файлы и результат тестов;
6. отдельно перечисляет уже существовавшие изменения, если они важны;
7. добавляет только файлы текущей итерации, создаёт атомарный commit и отправляет текущую ветку;
8. сообщает пользователю ветку, commit hash и результат push.

Постоянное разрешение на commit/push действует только для успешно законченной итерации этого проекта. Перед push агент проверяет remote, ветку, upstream и отсутствие неожиданной переписи истории. Merge, release и deploy остаются отдельными действиями и не следуют автоматически из push.

## 20. Критерии готовности Git-процесса

Git-процесс готов к командной работе, когда:

- `main` защищена;
- `.gitignore` и `.gitattributes` применены;
- реальные секреты отсутствуют в истории;
- CI запускает обязательные проверки;
- pull request template содержит проверки миграции, security и rollback;
- CODEOWNERS или эквивалентные review-правила назначены для чувствительных областей;
- documented release создаёт versioned artifacts;
- production deploy требует отдельного разрешённого действия;
- backup/restore и rollback проверены;
- новый сотрудник может клонировать проект и запустить development-среду по документации без получения production-секретов.
