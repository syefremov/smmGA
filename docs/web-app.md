# Внутренняя веб-панель

Этот документ фиксирует продуктовый, UX- и технический контракт внутренней веб-панели SMM GPT. Панель является дополнительным клиентом центральной системы: чат остаётся основным способом работы, а браузер даёт удобные визуальные представления для календаря, редактора, согласования, аналитики и администрирования.

## 1. Принципы

1. Чат и веб-панель работают с одной PostgreSQL и одним SMM Core.
2. Бизнес-правила реализуются на сервере один раз.
3. Браузер обращается только к версионированному Web API.
4. Наличие кнопки в интерфейсе не является разрешением: права всегда проверяет сервер.
5. Панель не должна требовать установки проекта на компьютер сотрудника.
6. Веб-интерфейс можно включать поэтапно, не блокируя chat-first MVP.
7. Опасные действия требуют ясного контекста и подтверждённого ответа сервера.
8. Интерфейс должен быть рабочим, доступным и быстрым, а не демонстрационным dashboard.

## 2. Что панель решает лучше чата

- обзор большого числа постов и задач;
- календарное планирование;
- перетаскивание и массовая фильтрация без потери контекста;
- сравнение редакций рядом;
- редактор текста и медиа с предпросмотром площадки;
- последовательное согласование очереди;
- просмотр временных рядов и сравнение экспериментов;
- управление источниками, документами, ролями и интеграциями;
- просмотр аудита и состояния фоновых задач.

Чат лучше подходит для постановки задач естественным языком, исследования, генерации идей, объяснения аналитики и быстрых единичных действий. Оба интерфейса должны свободно дополнять друг друга.

## 3. Визуальная и интерактивная концепция

### Визуальный тезис

Спокойная редакционная диспетчерская: светлая нейтральная поверхность, строгая типографика, высокая плотность полезной информации и один сдержанный акцент для основного действия. Интерфейс должен напоминать качественный рабочий инструмент, а не рекламную страницу.

### План содержания

Для приложения не используется маркетинговый hero. Первый экран сразу показывает рабочую поверхность:

1. навигацию и выбранное рабочее пространство;
2. очередь задач или календарь;
3. основные статусы и фильтры;
4. контекстный инспектор выбранного объекта;
5. одно очевидное основное действие.

### Интерактивный тезис

- выбор объекта плавно открывает контекстный инспектор без потери позиции списка;
- переход между редакциями использует короткую согласованную анимацию, помогающую увидеть смену версии;
- изменение статуса обновляет строку или календарный элемент только после подтверждения сервера;
- при `prefers-reduced-motion` необязательные переходы отключаются.

Анимация не используется для украшения таблиц, графиков или обычной навигации.

## 5. Ключевые пользовательские сценарии

### Вход и выбор рабочего пространства

1. Пользователь открывает HTTPS-адрес.
2. Сервер перенаправляет его к выбранному OIDC-провайдеру.
3. После входа сервер создаёт отзываемую сессию.
4. Пользователь видит только доступные workspace.
5. Последний workspace можно восстановить как предпочтение, но сервер заново проверяет membership.

Если доступа нет, показывается понятное состояние без утечки названий или данных чужих компаний.

### Создание поста

1. Пользователь выбирает бренд и площадки.
2. Создаёт пустой черновик или запускает генерацию.
3. Длительная генерация выполняется worker; интерфейс показывает статус задачи.
4. Полученный вариант сохраняется как новая неизменяемая редакция.
5. Пользователь редактирует рабочую копию и явно сохраняет новую редакцию.
6. Материал отправляется на согласование.

Незавершённый текст формы может временно храниться локально для восстановления после перезагрузки, но он явно помечается как локальный и не считается серверной редакцией.

### Согласование

Экран показывает:

- пост, бренд и площадку;
- номер и время конкретной редакции;
- полный текст и медиа;
- разницу с предыдущей редакцией;
- комментарии и проверяемые источники;
- предупреждения формата площадки;
- историю решений.

Кнопка одобрения отправляет `revision_id` и ожидаемую версию объекта. Если редакция уже изменилась, сервер отвечает конфликтом, а интерфейс требует перечитать новую версию.

### Планирование и публикация

Перед подтверждением показываются:

- точная одобренная редакция;
- социальный аккаунт и площадка;
- дата, время и часовой пояс;
- список медиа;
- известные предупреждения;
- режим: запланировать или опубликовать сейчас.

Интерфейс не показывает публикацию успешной, пока сервер не подтвердил результат. При неопределённом внешнем ответе состояние называется `проверяется`, а не `ошибка` или `опубликовано`.

### Работа с базой знаний

Пользователь видит документ, тип, источник, версию, актуальность, доступ и статус обработки. Загрузка файла создаёт фоновую задачу. Ошибка парсинга или embeddings не скрывается; последняя рабочая версия остаётся активной.

### Аналитика

Все графики показывают:

- период и часовой пояс;
- используемую формулу;
- размер выборки;
- отсутствующие данные;
- дату последней синхронизации;
- возможность открыть исходные публикации.

График не заменяет табличное или текстовое представление важных значений.

## 6. Frontend-архитектура

### Выбранный стек

- TypeScript в строгом режиме;
- React;
- Vite для разработки и production-сборки;
- TanStack Router для типизированных клиентских маршрутов;
- TanStack Query для серверного состояния;
- React Hook Form для управляемых форм;
- Zod для проверки данных на границе формы и runtime-проверок там, где они нужны;
- доступные headless-примитивы для dialog, menu, tabs, tooltip, combobox и focus management;
- CSS variables для дизайн-токенов и темы;
- Vitest и Testing Library для unit/component-тестов;
- Playwright для критических browser-сценариев.

Версии Node.js, package manager и зависимостей фиксируются при создании каркаса. Для воспроизводимости `package.json` содержит точное поле `packageManager`, lockfile хранится в Git, а CI использует ту же версию.

Это внутренняя SPA, поэтому SSR не нужен для SEO. Vite создаёт оптимизированные статические файлы, которые можно раздавать reverse proxy. Если позже появится публичная индексируемая часть, её следует проектировать отдельно, а не усложнять внутреннюю панель.

```text

├── features/
│   ├── auth/
│   ├── workspaces/
│   ├── dashboard/
```

## 7. Управление состоянием

Состояние разделяется явно:

- серверное состояние — TanStack Query;
- фильтры, открытый раздел и выбранная вкладка — URL;
- состояние формы — React Hook Form;
- краткоживущие визуальные состояния — локальный React state;
- подтверждённое бизнес-состояние — только сервер и PostgreSQL.

Глобальный клиентский store не добавляется по умолчанию. Он допустим только для действительно общего UI-состояния, которое невозможно разумно выразить через URL, query cache или локальный state.

Query keys всегда включают `workspace_id` и предметные фильтры. При смене workspace, выходе, истечении сессии или изменении прав чувствительный query cache очищается.

## 8. Web API

### Общие правила

- базовый путь `/api/v1`;
- JSON для предметных запросов;
- UTC и ISO 8601 на транспортном уровне;
- cursor pagination для растущих списков;
- стабильные машинные коды ошибок;
- correlation ID в ответе и журнале;
- OpenAPI является контрактом клиента;
- TypeScript-клиент генерируется в CI и проверяется на расхождения.

Пример ответа об ошибке:

```json
{
  "error": {
    "code": "revision_conflict",
    "message": "Появилась новая редакция поста.",
    "details": {
      "post_id": "...",
      "expected_revision": 7,
      "current_revision": 8
    },
    "correlation_id": "..."
  }
}
```

В `details` не возвращаются stack traces, SQL, токены или внутренние секреты.

### Команды и конкурентные изменения

Изменяющие запросы передают ожидаемую версию ресурса или `If-Match`. При конфликте сервер возвращает `409 Conflict`. Интерфейс показывает различия и не перезаписывает чужую работу автоматически.

Создание публикации и другие повторяемые внешние операции используют idempotency key. Повтор браузерного запроса после потери сети не должен создать дубль.

### Длительные операции

Сбор источника, генерация, экспорт, загрузка метрик и индексация возвращают `job_id`. Для прогресса используется SSE, если он действительно улучшает UX; обязательным остаётся обычный endpoint состояния задачи, чтобы восстановиться после перезагрузки или разрыва соединения.

### Группы endpoint

| Префикс | Назначение |
|---|---|
| `/api/v1/session` | текущая сессия, logout и CSRF bootstrap |
| `/api/v1/workspaces` | доступные workspace, предпочтения и capabilities |
| `/api/v1/brands` | профили брендов и правила |
| `/api/v1/products` | продуктовые версии, факты, claims и пробелы знаний |
| `/api/v1/campaigns` | цели, планы, work items, зависимости и блокеры |
| `/api/v1/agents` | профили, версии, запуски, artifacts, evals и предложения памяти |
| `/api/v1/posts` | посты, редакции, комментарии и переходы состояний |
| `/api/v1/approvals` | очередь и решения по конкретным редакциям |
| `/api/v1/publications` | расписание, отмена, попытки и внешние статусы |
| `/api/v1/sources` | источники, сбор и результаты |
| `/api/v1/knowledge` | документы, версии, поиск и переиндексация |
| `/api/v1/analytics` | метрики, сравнения, отчёты и эксперименты |
| `/api/v1/community` | входящие сообщения, reply drafts, consent и escalations |
| `/api/v1/media` | метаданные и управляемая загрузка файлов |
| `/api/v1/integrations` | состояния подключений без раскрытия секретов |
| `/api/v1/team` | участники, приглашения и роли |
| `/api/v1/audit` | доступный пользователю аудит |
| `/api/v1/jobs` | состояние и результат фоновых задач |

Конкретная команда оформляется отдельным endpoint действия или ясно определённым переходом, а не универсальным `PATCH`, позволяющим установить любой статус. Например, одобрение вызывает серверную операцию approve и не сводится к записи `status = approved`.

### Файлы и медиа

- сервер проверяет право и создаёт ограниченную загрузку;
- размер, MIME type, расширение и сигнатура файла валидируются;
- имя пользователя не становится путём в файловой системе;
- файлы проходят обработку и при необходимости антивирусную проверку;
- оригинал и производные версии имеют отдельные идентификаторы;
- загрузка в object storage использует короткоживущие подписанные URL либо поток через сервер;
- публичный URL не создаётся автоматически;
- удаление учитывает связи с редакциями и политику хранения.

## 9. Авторизация и сессии

Предпочтительная схема — OIDC Authorization Code Flow с PKCE и отдельным серверным session cookie. Конкретный OIDC-провайдер выбирается перед production; доменная модель не должна зависеть от него.

Cookie:

- `Secure`;
- `HttpOnly`;
- подходящий `SameSite`;
- узкий `Path` и без избыточного `Domain`;
- случайный идентификатор, не содержащий профиль пользователя;
- ограниченный абсолютный и неактивный срок жизни;
- ротация после входа и повышения привилегий.

Bearer- и refresh-токены не сохраняются в `localStorage`. Выход отзывает серверную сессию и очищает чувствительные клиентские кеши. Администратор может отозвать все сессии сотрудника.

Для критических операций можно включить недавнее повторное подтверждение личности. В первую очередь это относится к смене интеграционных секретов, выдаче административной роли и массовой публикации.

## 10. Авторизация и роли

Сервер проверяет membership и permission на каждом запросе. Frontend получает безопасное описание доступных capabilities и использует его для интерфейса, но не как единственную защиту.

Особенности:

- отсутствие права скрывает или отключает действие с понятным объяснением;
- прямой переход по URL всё равно проверяется сервером;
- данные одного workspace не остаются на экране после переключения;
- список социальных аккаунтов фильтруется по доступу;
- аудит ролей показывает автора, время и основание изменения;
- отзыв membership завершает активные сессии или делает их недействительными при ближайшей проверке.

## 11. Защита браузерного клиента

- один origin предпочтительнее сложной CORS-конфигурации;
- state-changing запросы защищаются CSRF-токеном или эквивалентной проверенной схемой;
- сервер проверяет `Origin` для чувствительных запросов;
- включаются CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy` и ограничения framing;
- HTML из источников не вставляется через небезопасный raw rendering;
- Markdown и rich text санитизируются по allowlist;
- внешние ссылки визуально обозначаются и используют безопасные параметры открытия;
- source maps production-сборки не публикуются без осознанного решения;
- frontend env не содержит секретов: всё попавшее в bundle считается публичным;
- API имеет ограничение частоты и размера запросов;
- чувствительные ответы используют подходящую cache policy;
- сервис worker/PWA не включается, пока не определены правила хранения приватных данных offline.

## 12. Редактор и версии

Начальная версия использует надёжный plain-text или ограниченный структурированный редактор. Полноценный WYSIWYG добавляется только при реальной необходимости, поскольку он усложняет переносимость текста между площадками, sanitization и сравнение редакций.

Правила:

- сохранение создаёт новую `post_revision`, а не перезаписывает старую;
- номер редакции и серверный статус всегда видимы;
- автосохранение сохраняет рабочую копию отдельно и не создаёт ложное одобрение;
- восстановленный локальный черновик сравнивается с текущей серверной версией;
- счётчики длины и ограничения зависят от целевой площадки;
- preview явно помечается как приблизительный;
- alt text и подписи медиа входят в проверку;
- изменение одобренной редакции инвалидирует одобрение на сервере.

## 13. Дизайн-система

### Композиция

- одна основная рабочая область на экран;
- минимум визуальных контейнеров;
- карточка используется только когда сама является интерактивной сущностью;
- таблицы, разделители и типографика предпочтительнее сетки декоративных карточек;
- главный action использует один акцентный цвет;
- опасные действия имеют отдельную семантику, но не конкурируют с основным акцентом повсюду;
- статусы различаются не только цветом, но текстом и при необходимости формой/iconography.

### Токены

CSS variables определяют:

- поверхности и уровни текста;
- accent, success, warning, danger и focus;
- типографическую шкалу;
- интервалы и размеры controls;
- радиусы, границы и тени;
- длительность и easing движения;
- ширины навигации и инспектора;
- breakpoints.

Не более двух семейств шрифтов. Основной интерфейс должен оставаться читаемым при системном fallback font.

### Темы

Светлая тема обязательна. Тёмная допускается после появления полного набора семантических токенов и автоматических проверок контраста. Нельзя создавать две независимо оформленные версии компонентов.

## 14. Адаптивность

### Политика браузеров

Поддерживаются последние две стабильные основные версии Chrome, Edge, Firefox и Safari, а также последние две основные версии iOS Safari и Chrome for Android. Фактические браузеры сотрудников фиксируются перед первым production-релизом. Internet Explorer и встроенные устаревшие WebView не поддерживаются.

Если корпоративный компьютер обновляется централизованно, его фактическая версия браузера входит в обязательную тестовую матрицу, даже если она выходит за общий диапазон.

### Режимы экрана

Поддерживаемые режимы:

- широкий desktop — навигация, рабочая область и инспектор одновременно;
- обычный laptop — сворачиваемая навигация и инспектор;
- tablet — рабочая область плюс drawer;
- mobile — одноуровневая последовательная навигация.

На телефоне обязательно доступны:

- вход и выбор workspace;
- рабочая очередь;
- просмотр поста и медиа;
- комментарий, одобрение или отклонение при наличии права;
- просмотр статуса публикации;
- экстренная отмена будущей публикации.

Массовое редактирование, сложные сравнения и полная административная настройка могут быть desktop-first, но мобильный пользователь получает понятное объяснение ограничения, а не сломанный интерфейс.

## 15. Доступность

Цель — WCAG 2.2 AA для поддерживаемых рабочих сценариев.

- корректная структура заголовков и landmarks;
- полная работа с клавиатуры;
- заметный focus без ловушек;
- подписи, описания и ошибки форм связаны программно;
- dialog возвращает фокус инициатору;
- таблицы имеют заголовки и доступное представление на узком экране;
- графики сопровождаются текстом или таблицей;
- drag-and-drop имеет кнопочную/клавиатурную альтернативу;
- уведомления об асинхронном результате объявляются без захвата фокуса;
- цвет не является единственным носителем смысла;
- touch targets достаточного размера;
- поддерживаются масштабирование текста и reduced motion;
- русские даты и числительные не мешают screen reader.

Автоматическая проверка помогает находить дефекты, но не заменяет ручной проход клавиатурой и screen reader по критическим сценариям.

## 16. Состояния интерфейса

Каждый экран проектируется не только для успешной загрузки:

- initial loading;
- background refresh;
- пустой список;
- нет результатов фильтра;
- частичные данные;
- устаревшие данные;
- offline или timeout;
- недостаточно прав;
- объект удалён или архивирован;
- `409` конфликт версии;
- `429` ограничение частоты;
- `5xx` и correlation ID;
- истекшая сессия;
- фоновая задача в очереди, выполняется, завершилась или требует внимания.

Повторная попытка не должна случайно повторять опасную команду. Для безопасных чтений повтор возможен автоматически; для внешних изменений используется идемпотентность и проверка серверного результата.

## 17. Даты, язык и часовые пояса

- API передаёт время в UTC;
- workspace и пользователь имеют явный IANA timezone;
- форма планирования всегда показывает зону;
- при переходе на летнее/зимнее время неоднозначное локальное время требует уточнения;
- интерфейс по умолчанию русский, строки вынесены в каталог локализации;
- машинные enum не используются как пользовательский текст;
- формат чисел, валют и дат определяется locale;
- пользовательский ввод не преобразуется молча между часовыми поясами.

## 18. Уведомления

Встроенный центр уведомлений показывает события, требующие действия: запрос согласования, неудачную публикацию, конфликт интеграции или завершение долгой задачи. Рутинные успешные фоновые обновления не должны создавать шум.

Email, Telegram-уведомления или push являются отдельными каналами с явными пользовательскими настройками. Секретные тексты и приватные материалы не включаются во внешнее уведомление без соответствующей политики.

## 19. Производительность

- маршруты и тяжёлые визуализации загружаются по требованию;
- списки используют серверную пагинацию и фильтрацию;
- изображения получают подходящие размеры и lazy loading;
- поиск отменяет устаревшие запросы;
- query cache имеет осознанные сроки свежести;
- массовые обновления не вызывают N+1 запросы из браузера;
- основной интерфейс остаётся работоспособным при медленном SSE или недоступной аналитике;
- production bundle и ключевые маршруты имеют бюджет размера и времени загрузки.

Оптимизация выполняется по измерениям. Виртуализация, сложная мемоизация и отдельный realtime-слой не добавляются заранее.

## 20. Тестирование

### Unit и component

- формы и ошибки;
- таблицы, фильтры и пагинация;
- permission-aware UI;
- timezone formatting;
- error boundary;
- восстановление черновика;
- доступное управление dialog, menu и combobox.

### Контракт

- OpenAPI генерируется сервером;
- TypeScript-клиент пересобирается в CI;
- незакоммиченная разница считается ошибкой;
- frontend fixtures соответствуют реальным схемам;
- серверные ошибки корректно отображаются по машинному `code`.

### Browser/E2E

- вход и выход;
- выбор и переключение workspace;
- создание и редактирование поста;
- конфликт двух редакторов;
- одобрение конкретной редакции;
- планирование и отмена;
- неопределённый результат публикации;
- загрузка и ошибка обработки документа;
- отзыв сессии;
- клавиатурный проход критического сценария;
- desktop, tablet и mobile viewport.

Обычные E2E используют fake-коннектор соцсети. Реальная тестовая публикация запускается отдельно и требует явной конфигурации песочницы.

### Визуальная проверка

Ключевые страницы проверяются скриншотами в стабильном окружении: рабочая очередь, календарь, редактор, согласование, аналитика и состояния ошибок. Снимки не заменяют поведенческие тесты.

## 21. Наблюдаемость

Frontend сообщает серверу безопасные технические события:

- версия сборки;
- маршрут и тип ошибки;
- correlation ID API;
- длительность ключевых запросов;
- отказ загрузки chunk;
- непойманная ошибка интерфейса.

Не отправляются тексты постов, документы, токены и персональные данные без отдельного основания. Логи клиента и сервера можно связать по correlation ID.

Health-информация в UI показывает только безопасный статус доступных пользователю интеграций и фоновых задач, а не внутреннюю топологию сервера.

## 22. Развёртывание

### Development

- Vite dev server используется локально;
- `/api` проксируется в FastAPI;
- fake OIDC или отдельный development realm;
- тестовые данные и fake social connector;
- никаких production-секретов.

### Production

```text
Internet
   ↓ HTTPS :443
Caddy/Nginx
   ├── /              → versioned static frontend build
   ├── /api/v1/*      → FastAPI
   ├── /events/*      → SSE with buffering disabled
   └── protected MCP  → MCP transport
```

Frontend собирается reproducibly в CI или multi-stage Docker build. Готовая сборка получает immutable hashed assets, а HTML — короткую cache policy, чтобы новая версия не ссылалась на удалённые chunks.

Миграции базы выполняются отдельным контролируемым шагом до переключения приложения. Изменения API должны быть обратно совместимы на время rolling deployment или разворачиваться в согласованном порядке.

### Конфигурация

В frontend bundle допустимы только публичные параметры:

- базовый публичный путь;
- безопасный идентификатор окружения;
- публичные feature flags;
- URL поддержки.

Секретные ключи, пароли, client secret OIDC и токены соцсетей существуют только на сервере.

## 23. Feature flags и поэтапное включение

Панель развивается вертикальными срезами:

1. оболочка, вход, workspace и read-only рабочая очередь;
2. пост, редакции и комментарии;
3. согласование;
4. календарь и планирование;
5. источники и база знаний;
6. кампании, специализированные AI-задачи и их artifacts;
7. аналитика и обратная связь;
8. интеграции, команда и аудит.

Незавершённые модули закрываются серверными feature flags и permissions. Скрытие пункта меню само по себе не считается защитой endpoint.

## 24. Миграция и совместимость с чатом

Каждая предметная возможность сначала определяется как доменная операция, затем получает MCP- и/или REST-представление. Один интерфейс может быть удобнее другого, но итоговые состояния совпадают.

Примеры:

| Операция | Codex | Веб-панель | Общий результат |
|---|---|---|---|
| Создать идею | разговорный запрос | форма или действие из источника | `content_idea` |
| Создать редакцию | просьба переписать | редактор | новая `post_revision` |
| Одобрить | явная команда | кнопка с подтверждением | `approval` для revision ID |
| Запланировать | команда с датой | календарь/форма | `publication` |
| Получить анализ | объяснение | графики и таблица | один расчёт SMM Core |

Нельзя реализовать действие только как frontend-запись непосредственно в таблицу или только как специальную ветку MCP handler.

## 25. Критерии готовности веб-панели

Панель готова к рабочему использованию, когда:

- сотрудник входит через персональную учётную запись;
- сервер изолирует workspace и проверяет каждое право;
- frontend не содержит секретов и не хранит bearer-токены в `localStorage`;
- смена workspace очищает чувствительное состояние;
- основные маршруты имеют loading, empty, error и conflict состояния;
- создание, редактирование и согласование используют неизменяемые редакции;
- публикация не может обойти одобрение;
- критические действия подтверждаются серверным результатом;
- интерфейс работает на заявленных desktop и mobile размерах;
- критические сценарии доступны с клавиатуры и соответствуют WCAG 2.2 AA;
- E2E не используют реальные соцсети по умолчанию;
- production-сборка воспроизводима и проходит через HTTPS;
- ошибки можно найти по correlation ID;
- процедура обновления и отката задокументирована и проверена.

## 26. Решения перед началом реализации

Нужно подтвердить:

1. домен или поддомен панели;
2. OIDC-провайдер и необходимость SSO/MFA;
3. первый вертикальный сценарий;
4. обязательный мобильный объём;
5. визуальные материалы бренда и желаемый акцент;
6. политика хранения локальных незавершённых черновиков;
7. каналы уведомлений;
8. требования к браузерам сотрудников;
9. нужна ли тёмная тема;
10. допустимый поставщик клиентской телеметрии или полный self-hosted режим.

Эти решения не меняют базовый принцип: браузер остаётся клиентом единого защищённого серверного ядра.
