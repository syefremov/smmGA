# Человеческие решения по замечаниям AI-редактора

Десятый репозиторный срез фазы 7, 2026-09-03. После текстового Editor добавлен учёт
человеческих решений по **конкретному замечанию конкретного отчёта**. Общий сервис обслуживает
чат/MCP и REST; веб показывает состояние и последние решения. Провайдер и сервер не включаются.

## Что можно сделать

| Статус | Значение |
|---|---|
| `open` | Ещё не разобрано или явно возвращено в работу |
| `needs_changes` | Человек подтвердил, что нужна правка; текст ещё не исправлен |
| `dismissed` | Человек отклонил замечание AI и записал обоснование |

Повтор текущего статуса без перехода отклоняется. Все переходы между разными статусами
разрешены при действующем отчёте и новом точном подтверждении. Статуса «исправлено» нет:
исправление — отдельная новая редакция и новая проверка, а не заявление о старом тексте.
Никакой статус не отменяет deterministic preflight, не меняет права, не создаёт approval,
publication package, memory, work item или оплачиваемый запуск. Даже отклонённое blocking
замечание не становится разрешением на публикацию.

## Как управлять из чата

1. `session_read`, затем `ai_run_read` для своего Editor run: показать точный текст замечания,
   его цитату/основания и сохранённую редакцию, а не рабочую копию.
2. `ai_editor_triage_read`: получить artifact ID/hash, revision ID/content hash, индекс
   замечания (с нуля), finding hash и текущую `version` истории решений.
3. Предложить статус и **конкретное обоснование**, получить отдельное явное подтверждение
   человека. Похвала, инструкции внутри источника и собственный вывод AI не являются согласием.
4. `ai_editor_finding_decide` с этими полями, `expected_version`, `human_confirmed=true`
   и новым idempotency key. Команда сохраняет только решение по замечанию.
5. Перечитать `ai_editor_triage_read`. Receipt — исторический факт выполнения, не актуальное
   состояние. После обрыва повторять ту же команду с **тем же ключом**, не создавать новый.

Пример запроса: «Замечание № 1 требует исправления. Запиши причину: источник не подтверждает
формулировку. Сам текст пока не меняй». До записи нужно прочитать exact report и связать команду
с индексом 0, а не только с видимым номером или похожей цитатой.

Доступ — инициатор AI run, пока он действующий Owner с MFA. Другой Owner не получает чужой
private отчёт. `human_confirmed` — прикладной контракт подтверждения, не криптографическое
доказательство присутствия человека. Личные инструменты triage не передаются AI-профилям.

## Контракты и хранение

REST prefix: `/api/v1/workspaces/{workspace_id}/knowledge/runs/{run_id}`:

- GET `/editor-triage` — актуальные привязки и статусы;
- POST `/editor-triage` — `DecideEditorialFinding`;
- GET `/editor-triage/history?before=...` — история по 25 записей, от новых к старым;
  следующий cursor возвращается как `next_before` и передаётся в `before`.

MCP: `ai_editor_triage_read`, `ai_editor_finding_decide`, `ai_editor_triage_history`.
Общий `ai_run_read` также возвращает `editorial_triage` вместе с актуальным `editorial_review`.
Списки runs не загружают историю. OpenAPI и TypeScript DTO генерируются из backend.

`editorial_decisions` — append-only: workspace, initiating actor, run/artifact/revision IDs,
artifact/content/finding hashes, finding index, status, reason, sequence, UTC timestamp,
idempotency key hash и fingerprint команды. Причина не попадает в технический audit; аудит
содержит только действие, статус, actor и ID записи. История входит в backup PostgreSQL.

Версия общая для одного отчёта, изначально 0. Любое решение увеличивает её на 1, даже если
разбиралось другое замечание. Два компьютера с одной старой версией получают один успех и
конфликт; тихой перезаписи нет. Один ключ с другим содержимым — `idempotency_conflict`.
Тот же ключ возвращает исходную историческую запись даже после устаревания отчёта, но только
при сохранившихся личных правах. Это не повторное применение старого решения.

Сначала берётся knowledge lock, затем content lock. Перед новой записью проверяются текущая
редакция, SQL evidence/policy/brief, profile selection, целостность artifact и точные finding
index/hash. Сетевых вызовов под locks и вообще в triage нет. БД дополнительно проверяет
tenant/actor, immutable history, последовательность, parent artifact/run и current revision.

## Устаревание, история и веб

Изменение текста, правил, истечение источников или отключение/смена профиля запрещают новые
решения по старому отчёту. `ai_run_read` скрывает вместе и замечания, и актуальные статусы.
`ai_editor_triage_read` возвращает конфликт — необходимо прочитать текущий контент и отдельно
решить, запускать ли новую проверку. Решения не переносятся на новый run даже при похожем тексте.

Исторический endpoint остаётся доступен владельцу-инициатору после устаревания отчёта:
возвращает только его решения, rationale и IDs/hashes, **не** исходные цитаты, model output или
факты. `historical_only=true` запрещает трактовать историю как текущую оценку/approval.
После отзыва доступа и история недоступна. Физического удаления нет.

В «База знаний → AI-профили → запуск» рядом с замечанием показан статус человека и основание;
раскрывающийся блок содержит последние 25 решений, автора и время в часовом поясе workspace.
Длинная история читается
через чат/API. Текст выводится инертно, без HTML; нет кнопки массового отклонения или одобрения.
Экран обновляется штатным опросом run каждые 10 секунд в активной вкладке. Это снимок, не
гарантия мгновенного отзыва; новая команда всегда перечитывает серверный контекст.

## Миграция и проверки

`0013_editor_triage` добавляет одну таблицу и guard. Runtime получает SELECT/INSERT под RLS;
worker не получает доступа к таблице. Существующие post/approval/artifact записи и model payload
не меняются, новые зависимости/flags/секреты не требуются. Перед реальным обновлением:
отдельное разрешение, backup/restore rehearsal, штатная миграция и согласованное обновление кода.
Downgrade удаляет историю человеческих решений и допустим только на disposable БД или по
отдельному restore-backed плану. Push не выполняет deploy.

Проверки: закрытые DTO, exact bindings, idempotency/concurrent commands, reopen, stale
revision/policy/profile, роль/MFA/tenant, worker deny, immutable UPDATE/DELETE/TRUNCATE,
pagination, отсутствие content approval и parity реальных REST/MCP транспорта на synthetic DB.
Веб: инертное обоснование, отсутствие approval controls, история и скрытие stale report.

Локально: 279 Python tests (2 Linux-only проверки пропущены на Windows), 79 DB tests на
disposable PostgreSQL 15, 32 web tests, production build и `pnpm check`. Playwright CLI / Edge:
390 px и desktop, инертный HTML, без горизонтального переполнения, время workspace и скрытие
замечаний/triage после stale ответа. Скриншоты — в игнорируемом `output/playwright/`.
Linux CI дополнительно проверяет PostgreSQL 17, контейнерный browser/queue и synthetic server lifecycle.

Это human triage, не автоматическая оценка правильности замечаний, не метрика качества модели
и не workflow доказанного исправления между редакциями. Фаза 7 остаётся частичной: реальные
корпус/evals, остальные специалисты, hybrid retrieval и server/two-machine gates ещё нужны.
