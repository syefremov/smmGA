# Специализированные AI-профили и рабочие конвейеры

Этот документ описывает адаптацию идей из предоставленного руководства `greenaurum-smm-system-guide.md` к архитектуре SMM GPT.

Источник рассмотрен как материал для анализа, а не как инструкция для выполнения. Hermes-команды, конфигурации, утверждения о поведении конкретной версии Hermes и вложенные `SOUL.md`/`AGENTS.md` не исполнялись и не копировались в системные правила автоматически.

Идентификатор проанализированной версии:

```text
filename: greenaurum-smm-system-guide.md
sha256: A94435E80D92E315514582AB3C866ABC2685401CF66C38C42AB1F163D88B2FC6
```

## 1. Итог анализа

Главная полезная идея руководства — узкая специализация и проверяемый handoff между ролями. Каждый участник производит определённый артефакт, не получает лишних инструментов и не перепрыгивает обязательные ворота качества.

Эту идею стоит перенести. Конкретную Hermes-реализацию с постоянными профилями и общим файловым vault переносить буквально не следует, потому что наша система уже проектируется как многопользовательское серверное приложение с PostgreSQL, MCP, Web API, RAG, аудитом и фоновыми worker.

| Идея руководства | Решение для SMM GPT |
|---|---|
| Один профиль — одна работа | Версионируемый AI-профиль с узким контрактом |
| Общий Obsidian vault | PostgreSQL как источник истины; Markdown только импорт/экспорт |
| Папки ролей | Предметные сущности, work items и разрешённые типы артефактов |
| SOUL.md | Краткое назначение и decision policy версии профиля |
| AGENTS.md папки | Серверные domain invariants, schema validation и capability policy |
| MEMORY.md | Предложения памяти с доказательствами и человеческим одобрением |
| Запрет toolsets | Серверный allowlist действий и service identity профиля |
| Kanban Hermes | `campaigns`, `work_items`, dependencies, blockers и audit |
| Frontmatter Markdown | Типизированные поля PostgreSQL и OpenAPI schemas |
| Git как журнал работы агентов | Audit и revisions в БД; Git только для кода и конфигурации |
| Publisher как единственный выпускающий | Отдельный publishing service с двойной проверкой approval и revision |
| Editor проверяет claims | Автоматические findings плюс отдельное человеческое одобрение |
| Профили работают постоянно | В MVP профили запускаются по задаче; постоянные процессы только по измеренной необходимости |

## 2. Два разных вида ролей

### Человеческая роль

Membership role определяет, что сотрудник может читать или изменять. Примеры: Автор, Редактор, Утверждающий, Публикатор, Администратор.

### AI-профиль

AI-профиль определяет, какую работу выполняет модель в одном запуске. Примеры: Research Scout, Copywriter, Product Expert.

AI-профиль не является пользователем и не получает права по названию. Он запускается:

- от имени конкретного разрешённого запроса пользователя;
- либо как серверная фоновая задача с ограниченной service identity;
- только с перечисленными capabilities;
- только внутри одного `workspace_id`;
- с обязательным audit trail.

Например, AI-профиль `Publisher` может подготовить и проверить пакет, но публикация всё равно требует серверно подтверждённого человеческого approval конкретной редакции и разрешения вызывающего пользователя.

## 3. Как профили исполняются

На первом этапе профиль — это запись и версия конфигурации, а не отдельный постоянно работающий агент.

```text
пользователь или scheduler
  → создаёт work item
  → сервер проверяет workspace, права и входы
  → выбирает активную версию AI-профиля
  → собирает минимальный разрешённый контекст
  → запускает модель/worker
  → валидирует структурированный результат
  → сохраняет ai_run и artifacts
  → применяет quality gate
  → передаёт результат человеку или следующей задаче
```

Преимущества такого подхода:

- единое управление из Codex и веб-панели;
- нет десяти независимых директорий и процессов;
- состояние видно всем разрешённым сотрудникам;
- права проверяются сервером;
- профили и результаты версионируются;
- можно менять модель отдельно от бизнес-данных;
- проще оценивать качество и стоимость каждой роли;
- позже один профиль можно вынести в отдельный worker без изменения предметного контракта.

## 4. Контракт профиля

Каждая версия `agent_profile` содержит:

- `name` — стабильное машинное имя;
- `display_name` — пользовательское название;
- `purpose` — одна основная задача;
- `scope` — workspace, brand и допустимые сущности;
- `accepted_inputs` — типизированные входы;
- `required_context` — обязательные источники;
- `output_schema` — проверяемый структурированный результат;
- `allowed_capabilities` — разрешённые domain-команды и чтение;
- `denied_capabilities` — явные запреты;
- `decision_policy` — правила выбора и обработки неопределённости;
- `quality_gates` — условия принятия результата;
- `escalation_policy` — когда нужен человек или другой профиль;
- `model_policy` — допустимые модели и режимы;
- `prompt_template_version`;
- `evaluation_suite_version`;
- `status` — draft, testing, active, retired;
- `created_by`, `approved_by`, `created_at`.

Активированная версия неизменяема. Изменение инструкции создаёт новую версию и требует повторных evals. Новый запуск сохраняет точную версию профиля, модели, входов и найденного RAG-контекста.

## 5. Общий конвейер контента

```text
цель кампании
  → Research Scout / Analyst
  → Product Expert и подтверждённые факты
  → Content Planner и brief
  → Copywriter и immutable revision
  → Visual Creator и media candidates
  → Editor/Compliance findings
  → исправление при необходимости
  → human approval конкретной revision
  → Publisher preflight/package
  → schedule/publish
  → metric snapshots
  → Analyst
  → memory proposals и следующий эксперимент
```

Не каждый пост обязан проходить все AI-профили. Сервер строит необходимый маршрут по типу задачи, но обязательные проверки фактов, прав и approval не отключаются ради скорости.

## 6. Реестр профилей

### 6.1 Research Scout

Назначение: найти и структурировать разрешённые внешние материалы.

Входы:

- исследовательский вопрос;
- бренды, темы, конкуренты и период;
- список разрешённых источников;
- требования к свежести.

Выходы:

- `research_finding`;
- исходные `source_item`;
- краткое утверждение;
- уровень доказательности;
- дата и область применимости;
- противоречия;
- идеи применения в контенте.

Ограничения:

- не создаёт продуктовый факт без проверки Product Expert;
- не публикует;
- не представляет рекламное утверждение конкурента как факт;
- не скрывает отсутствие первоисточника;
- использует только разрешённый способ сбора.

Уровни результата:

- `verified` — подтверждено допустимым авторитетным источником;
- `supported` — подтверждается несколькими источниками, но остаются ограничения;
- `observed` — наблюдение из контента/рынка, не универсальный факт;
- `unverified` — не удалось надёжно подтвердить;
- `conflicting` — источники расходятся.

### 6.2 Analyst

Назначение: превратить метрики в воспроизводимый отчёт и проверяемые гипотезы.

Входы:

- `metric_snapshots`;
- публикации и их признаки;
- период и timezone;
- данные продаж или переходов, когда они законно доступны;
- активные эксперименты.

Выходы:

- сводка;
- таблица метрик и дельт;
- лучшие/худшие сопоставимые материалы;
- ограничения выборки;
- гипотезы, а не ложные причинные выводы;
- рекомендации с обоснованием;
- список недостающих данных.

Ограничения:

- не заполняет пропуски выдуманными цифрами;
- не смешивает несопоставимые периоды или определения метрик;
- не выдаёт корреляцию за доказанную причину;
- не меняет контент-план напрямую без принятого решения.

### 6.3 Content Planner

Назначение: превратить цели и доказательные входы в контент-план и briefs.

Входы:

- цель и KPI кампании;
- бренд и площадки;
- продуктовые приоритеты;
- доступная производственная ёмкость;
- результаты Research Scout и Analyst;
- рубрики и ограничения частоты.

Выходы:

- версия `content_plan`;
- `content_slots`;
- brief каждого слота;
- цель, аудитория, формат и CTA;
- ссылки на факты и источники;
- зависимости от медиа, продукта или согласования;
- ожидаемый эксперимент.

Ограничения:

- не пишет финальные тексты;
- не обещает неподтверждённые акции или даты;
- не создаёт слоты без ответственного и состояния;
- не меняет опубликованную историю.

Баланс рубрик является настройкой бренда, а не универсальным числом, зашитым в профиль.

### 6.4 Product Expert

Назначение: поддерживать проверенные сведения о продуктах, услугах, применении и ограничениях.

Входы:

- документы владельца;
- карточки продукта и составы;
- официальные инструкции;
- подтверждённые Research findings;
- вопросы сотрудников и аудитории.

Выходы:

- версия продукта;
- атомарные `product_facts`;
- FAQ;
- безопасные инструкции применения;
- применимые claim rules;
- `knowledge_gap`, если данных недостаточно.

Ограничения:

- неизвестное не восстанавливается по похожим продуктам;
- факт без источника не становится `verified`;
- профиль не объявляет юридическую допустимость без утверждённой policy;
- медицинские и иные чувствительные вопросы эскалируются человеку соответствующей квалификации.

Каждый факт имеет владельца, источник, статус, дату проверки и при необходимости срок действия.

### 6.5 Copywriter

Назначение: создать новую редакцию по утверждённому brief.

Обязательный контекст:

- brand voice;
- площадка и ограничения формата;
- действующая версия brief;
- продуктовые факты;
- claim policies;
- разрешённые research sources;
- точные акция, ссылка и дедлайн, если они нужны.

Выходы:

- текст редакции;
- варианты начала/заголовка;
- CTA;
- media brief;
- ссылки на подтверждающие факты;
- предупреждения и непокрытые пробелы.

Ограничения:

- создаёт только новую revision;
- не публикует и не одобряет;
- не придумывает отзыв, цену, состав, сертификат, статистику или срочность;
- не заменяет запрещённый claim скрытым эквивалентом;
- при серой зоне выбирает осторожный вариант и создаёт finding/gap.

### 6.6 Visual Creator

Назначение: создать или подготовить визуальные варианты для конкретной редакции.

Выход хранит:

- `post_revision_id`;
- media brief;
- полный prompt и negative constraints;
- модель и параметры;
- исходные изображения и разрешения на их использование;
- generation identifier;
- alt text;
- связь вариантов и выбранного результата;
- необходимость disclosure, если она установлена policy.

Ограничения:

- не искажает реальные фото продукта до вводящего в заблуждение результата;
- не создаёт фиктивные before/after или отзывы;
- не генерирует логотипы/лица/объекты с неизвестными правами без проверки;
- не публикует;
- не меняет текст редакции.

### 6.7 Editor / Compliance Reviewer

Назначение: провести независимую проверку конкретной revision.

Категории checks:

- факты и источники;
- claims/compliance;
- tone of voice;
- правила площадки;
- цена, акция, ссылка и срок;
- соответствие визуала продукту;
- alt text и доступность;
- персональные данные, отзывы и согласия.

Каждый `review_finding` содержит:

- категорию;
- severity: info, warning, blocking;
- точное место;
- описание проблемы;
- policy/source;
- безопасное предложение исправления;
- статус разрешения.

Профиль возвращает рекомендацию `pass`, `needs_changes` или `needs_human_decision`. Это не запись `approval`. Человеческий утверждающий должен отдельно одобрить точную неизменяемую редакцию.

Reviewer не правит текст молча: исправление создаёт новую revision и запускает проверку заново.

### 6.8 Publisher

Назначение: собрать проверенный пакет и выполнить разрешённую публикацию.

Publication package включает:

- exact revision;
- действующий human approval;
- площадку и social account;
- media assets в порядке отправки;
- ссылки и результаты проверки;
- промокоды и сроки;
- planned time и timezone;
- idempotency key;
- результат preflight.

Перед внешним действием сервер повторно проверяет:

1. revision не изменилась;
2. approval относится к этой revision и не отозван;
3. вызывающий пользователь имеет право;
4. destination совпадает с подтверждённым;
5. ссылки, акции и обязательные данные актуальны;
6. такая публикация ещё не была успешно выполнена;
7. неизвестная предыдущая попытка сначала сверена с API площадки.

Publisher не редактирует approved-текст. Найденная ошибка возвращает материал в review и инвалидирует дальнейший выпуск.

### 6.9 Community Manager

Назначение: готовить ответы на разрешённые входящие сообщения и превращать обратную связь в знания.

Режим MVP — draft only. Отправка ответа наружу является отдельным подтверждённым действием.

Выходы:

- черновик ответа;
- ссылки на продуктовые факты;
- тональность и тип вопроса;
- необходимость эскалации;
- повторяющаяся тема;
- кандидат в FAQ или контент-идею;
- отметка о необходимости согласия для использования отзыва/UGC.

Ограничения:

- не диагностирует и не даёт персональный медицинский/юридический/финансовый совет;
- не обещает возврат, скидку, срок или компенсацию без полномочий;
- не спорит с пользователем и не скрывает негатив из отчёта;
- не переносит отзыв в рекламу без `consent_record` и применимой policy;
- минимизирует хранение персональных данных.

Сложный вопрос создаёт `escalation` с безопасным временным ответом, ответственным и сроком.

### 6.10 Orchestrator

Назначение: декомпозировать кампанию, строить зависимости, запускать разрешённые задачи и показывать блокеры.

Orchestrator может:

- предложить work breakdown;
- подобрать профиль по его контракту;
- создать draft work items;
- отслеживать фактические artifacts и статусы;
- выявлять циклы, пропавшие входы и узкие места;
- эскалировать решение с вариантами.

Orchestrator не может:

- выполнить работу специалиста «для скорости»;
- сам одобрить план, редакцию или публикацию;
- убрать обязательный quality gate;
- считать задачу готовой без валидного artifact;
- бесконечно создавать дубли задач;
- скрыть просроченный blocker.

Его следует включать последним. До этого пользователь или простой workflow service запускает профили явно.

## 7. Кампании, задачи и handoff

### Кампания

`campaign` хранит:

- бизнес-цель;
- период;
- бренды и площадки;
- KPI и способ измерения;
- ответственного человека;
- бюджетные/правовые ограничения;
- status;
- active plan version.

### Work item

`work_item` хранит:

- тип задачи;
- исполнителя: человек, AI-профиль или системный worker;
- необходимые входы;
- ожидаемый output schema;
- зависимости;
- дедлайн;
- priority;
- status;
- blocker reason и `blocked_since`;
- retry policy;
- correlation ID.

### Статусы

```text
proposed → ready → running → needs_review → completed
                 ↘ blocked
                 ↘ failed
proposed/ready/blocked → cancelled
```

`completed` допустим только при наличии валидного `run_artifact`. Устное сообщение модели «готово» статус не меняет.

### Зависимости

- граф не должен содержать циклов;
- отмена входа пересчитывает downstream tasks;
- новая версия исходного документа помечает зависимый результат потенциально stale;
- обязательный blocker не обходится без записанного решения человека;
- повторный запуск создаёт новый `ai_run`, а не перезаписывает старый.

## 8. Система продуктовых фактов и claims

Универсальный `brand_rules` недостаточен для чувствительных отраслей. Нужны два слоя.

### Product facts

Точный проверяемый факт: состав, характеристика, инструкция, ограничение, цена, ссылка или срок акции.

Статусы:

- `draft`;
- `verified`;
- `disputed`;
- `expired`;
- `archived`.

### Claim policy

Версионированное правило о том, какие формулировки допустимы для категории, бренда, продукта, площадки и юрисдикции.

Policy содержит:

- область применения;
- владельца;
- авторитетный источник;
- дату проверки;
- effective dates;
- запрещённые и требующие проверки patterns;
- допустимые альтернативы;
- обязательные disclaimers;
- процедуру human override;
- уровень severity.

Примеры из присланного файла про косметику рассматриваются как кандидаты для policy, а не как подтверждённое юридическое заключение. Перед рабочим использованием их проверяет назначенный владелец по актуальным авторитетным источникам.

Human override не стирает finding. Решение, автор, основание и версия policy остаются в аудите.

## 9. Память без неконтролируемого дрейфа

**Реализовано в седьмом срезе фазы 7:** Owner-only proposal/review → отдельно подтверждённый
новый неактивный `reference` с immutable provenance. Порядок команд, evidence/expiry/visibility,
раздельная activation и ограничения — [`memory-curation.md`](memory-curation.md).
`accept_for_curation` не разрешает импорт автоматически. Преобразования в brand rule,
product fact/evaluation case и произвольный profile/product/platform scope ниже остаются целевыми.

Профиль не редактирует постоянные правила напрямую.

После задачи он может создать `memory_proposal`:

- наблюдение;
- evidence links;
- scope: workspace, brand, product, platform или profile;
- confidence;
- proposed action;
- effective period;
- автор запуска;
- риск применения.

Человек или назначенный владелец:

- отклоняет proposal;
- принимает как knowledge document;
- превращает в brand rule;
- превращает в product fact;
- добавляет в evaluation case;
- устанавливает срок повторной проверки.

Временное предпочтение одного пользователя не становится правилом всего бренда автоматически. Слабая корреляция метрик не становится постоянной рекомендацией без эксперимента.

## 10. Источники, пробелы и происхождение

Каждое проверяемое утверждение должно вести к одному из:

- `product_fact`;
- `claim_rule`;
- `source_item`;
- `knowledge_chunk` с документом и версией;
- точному сообщению владельца, сохранённому как разрешённый input artifact.

Если подтверждения нет, создаётся `knowledge_gap`:

- что неизвестно;
- для какого действия это нужно;
- кто может предоставить данные;
- временный безопасный вариант;
- blocker severity;
- due date.

Механика gap полезнее общего запрета «не галлюцинировать»: она даёт системе следующий проверяемый шаг.

## 11. Проверки контента

`run_content_preflight` запускает детерминированные и AI-проверки отдельно.

Детерминированные проверки:

- наличие active revision;
- права и workspace;
- platform length/format limits;
- обязательные поля;
- срок акции;
- схема URL и allowlist доменов;
- media count/type;
- наличие alt text;
- валидный approval для publish path;
- idempotency.

AI-проверки:

- соответствие tone of voice;
- поддержка claims источниками;
- потенциально вводящие в заблуждение формулировки;
- конфликт текста и визуала;
- признаки вымышленного отзыва или чрезмерной уверенности;
- ясность CTA.

AI finding не является доказанным нарушением. Он показывает место, основание и severity для проверки.

## 12. Работа с визуалом

Визуал является версионируемым артефактом, а не безымянным файлом.

Обязательно сохраняются:

- автор или профиль;
- источник и права каждого input asset;
- prompt и параметры генерации;
- модель/инструмент;
- связь с brand style version;
- связь с post revision;
- alt text;
- размер и производные версии;
- review status;
- consent/disclosure, если применимо.

Финальный выбор делает человек или разрешённый процесс. Генерация нового варианта не заменяет ранее согласованный media asset в publication package.

## 13. Работа с обратной связью

Источники обратной связи подключаются через официальные API или ручной импорт. До хранения применяются правила минимизации персональных данных и retention.

Пайплайн:

```text
incoming message/review
  → classification
  → product facts + brand voice retrieval
  → reply draft
  → escalation when needed
  → human approval/send policy
  → outcome
  → anonymized insight cluster
  → FAQ/content idea/memory proposal
```

Повторяющиеся вопросы группируются только при сохранении ссылок на исходные сообщения. Порог превращения вопроса в тему настраивается по workspace; он не зашивается универсально как «ровно три раза».

## 14. Интерфейс в Codex и веб-панели

### Codex

Примеры команд:

```text
Создай кампанию для нового продукта на четыре недели.
Покажи предложенный план задач и блокеры, ничего пока не запускай.
Запусти Product Expert для проверки карточки продукта.
Подготовь три briefs из подтверждённых находок.
Проведи preflight редакции 12 и покажи blocking findings.
Покажи, какие предложения памяти ждут решения.
```

Перед массовым запуском Orchestrator показывает план и ожидаемые внешние/платные действия.

### Веб-панель

Добавляются представления:

- Campaign board с зависимостями;
- очередь work items и blockers;
- registry профилей и versions;
- run detail: входы, источники, результат, стоимость и artifacts;
- product facts и knowledge gaps;
- compliance findings;
- memory proposal inbox;
- community reply queue и escalations;
- publication package checklist.

UI не позволяет вручную поставить `completed` без artifact или `approved` без отдельной серверной операции.

## 15. MCP и API-контракт

Новые операции группируются по назначению:

### Campaigns

- create/read/update campaign;
- propose/approve plan version;
- list work items and blockers;
- cancel allowed pending work.

### Agent runs

- list profiles and active versions;
- start allowed task;
- read run status and artifacts;
- review result;
- retry with a new run;
- compare profile versions on evals.

### Products and policies

- manage product versions and facts;
- record/resolve knowledge gaps;
- manage claim policies through authorized workflow;
- explain applicable rules for a revision.

### Review and publishing

- run preflight;
- list/resolve findings;
- create human approval;
- build package;
- schedule/publish with idempotency.

### Community

- import permitted messages;
- draft replies;
- create/resolve escalation;
- record consent;
- produce anonymized insights.

MCP и REST endpoints вызывают одни и те же domain services. Универсального endpoint «выполни произвольный профиль с произвольными инструментами» быть не должно.

## 16. Оценка качества профилей

Для каждой версии нужен отдельный evaluation set.

Общие категории:

- schema validity;
- соблюдение capability boundaries;
- ссылки на существующие разрешённые источники;
- отсутствие выдуманных фактов;
- корректная эскалация;
- отсутствие cross-workspace leakage;
- обработка stale/conflicting inputs;
- стоимость и latency;
- устойчивость к prompt injection из источников.

Профильные примеры:

| Профиль | Критический eval |
|---|---|
| Research Scout | Отделяет рекламный claim от подтверждённого факта |
| Analyst | Не делает причинный вывод из одной корреляции |
| Planner | Не планирует неподтверждённую акцию |
| Product Expert | Создаёт gap вместо выдуманного состава |
| Copywriter | Использует только разрешённые факты и не публикует |
| Visual Creator | Сохраняет provenance и не имитирует ложный результат |
| Reviewer | Находит blocking claim и не создаёт human approval |
| Publisher | Отказывается от stale/неодобренной revision |
| Community Manager | Эскалирует чувствительный персональный вопрос |
| Orchestrator | Не обходит профиль и quality gate ради дедлайна |

Профиль переходит из `testing` в `active` только после согласованного порога evals и smoke-теста в реальном workspace без внешней публикации.

## 17. Наблюдаемость и стоимость

Для каждого запуска видны:

- profile/version;
- initiating user/job;
- workspace/brand;
- model/version;
- input artifact IDs;
- retrieval run;
- output artifacts;
- tokens/cost;
- latency;
- retries;
- validation и findings;
- final human disposition.

Дорогой или нестабильный профиль можно отключить независимо. Scheduler имеет лимиты workspace, чтобы ошибочный цикл не запускал бесконечные AI-задачи.

## 18. Порядок внедрения

### Фаза A — предметные основания

- products и product facts;
- claim policies;
- campaigns, work items и dependencies;
- registry и versions профилей;
- run artifacts и memory proposals;
- fake model/fake connector tests.

### Фаза B — безопасное ядро контента

- Product Expert;
- Research Scout;
- Content Planner;
- Copywriter;
- Editor/Compliance Reviewer;
- Publisher только в режиме package/manual posting.

### Фаза C — данные и визуал

- Analyst на реальных metric snapshots;
- Visual Creator с provenance;
- публикация через sandbox/официальный API;
- evals и cost dashboard.

### Фаза D — обратная связь

- ручной импорт комментариев/отзывов;
- Community Manager draft-only;
- escalations, consents и anonymized insights;
- затем read integration;
- отправка ответов только после отдельного решения и проверки policy.

### Фаза E — оркестрация

- Campaign board стабилен;
- минимум несколько профилей проходят evals;
- quality gates реализованы сервером;
- Orchestrator сначала предлагает план без запуска;
- затем получает право запускать только безопасные внутренние задачи;
- внешние действия остаются за отдельными подтверждёнными командами.

## 19. GreenAurum как первый workspace

GreenAurum выбран первым пилотным workspace, а ВКонтакте — первой социальной сетью. Руководство даёт хороший сценарий, но содержащиеся в нём сведения не считаются автоматически подтверждёнными.

До генерации рабочего контента потребуются:

1. импорт актуальных карточек продуктов из первичных материалов;
2. отдельная проверка составов/INCI и инструкций;
3. утверждённый brand voice с хорошими и плохими примерами;
4. claim policy, проверенная ответственным человеком по актуальным источникам;
5. действующие ссылки, цены и сроки акций как отдельные versioned facts;
6. доступ к официальному connector ВКонтакте на соответствующем этапе;
7. разрешённые выгрузки Wildberries для начальной аналитики;
8. применение утверждённой политики обработки отзывов, персональных данных и согласий;
9. тестовый набор постов, вопросов и ожидаемых review findings.

Предлагаемый первый вертикальный сценарий:

```text
карточка одного продукта
  → проверенные факты + gaps
  → один brief
  → три draft revisions
  → automated review findings
  → human correction/approval
  → publication package без автопостинга
```

Он проверяет основную ценность подхода без риска реальной публикации.

## 20. Что сознательно не переносится

- обязательная зависимость от Hermes Agent;
- предположение, что один профиль обязательно равен одному процессу;
- Obsidian vault как рабочая база;
- Git как журнал пользовательских данных;
- свободное чтение всеми профилями всех материалов;
- самостоятельное редактирование постоянной памяти;
- неподтверждённые имена toolsets и config keys;
- продуктовые, юридические или платформенные утверждения без актуальной проверки;
- дублирование больших persona-файлов в каждом запросе;
- универсальные числовые нормы длины поста, рубрик или порогов вопросов без настройки бренда;
- прямое доверие статусу, записанному моделью в Markdown.

## 21. Критерии готовности многоагентного контура

Контур готов, когда:

- human roles и AI profiles разделены в модели данных и интерфейсе;
- каждая active profile version прошла eval suite;
- capabilities ограничены сервером, а не только prompt;
- handoff выполняется через work items и typed artifacts;
- task graph защищён от циклов и дублей;
- продуктовые факты имеют provenance, а неизвестное становится gap;
- automated findings не подменяют human approval;
- Publisher не меняет revision и не обходит двойную проверку;
- память активируется только после review;
- все runs, расходы и результаты доступны в аудите;
- Orchestrator не может выполнить specialist action или снять quality gate;
- chat и web показывают одно серверное состояние;
- backup/restore восстанавливает profiles, tasks, artifacts и audit.
