# Загрузка документов сотрудником — шестой срез фазы 7

Дата: 2026-09-03. Реализован браузерный клиент существующего binary ingestion.
Фаза 7 остаётся частичной. Реальный сервер, identity rollout, ClamAV и платные провайдеры
в этой итерации не включались. Схема БД, API-контракты и зависимости не менялись.

Расширение пятнадцатого среза: добавлены UTF-8 Markdown/CSV/пассивный HTML —
[`knowledge-text-files.md`](knowledge-text-files.md). Обновлены generated format enums,
добавлена migration `0018_text_files`; правила переноса/identity/cache остаются прежними.

## Пользовательский сценарий

1. Войти в приватную панель своей учётной записью и выбрать workspace.
2. Открыть `/app/knowledge` → «Файлы». Вкладка доступна с `knowledge.write`;
   каждый запрос дополнительно авторизуется сервером, включая MFA для Owner.
3. Выбрать бренд и локальный PDF/DOCX/Markdown/CSV/HTML, до 2 МиБ. Для длинного списка брендов есть страницы.
   Клиент проверяет размер, имя, расширение/magic или UTF-8, читает реальные байты, считает SHA-256 и base64.
   Это удобство формы, **не** антивирус и не замена серверной проверке.
4. «Загрузить файл» отправляет существующий `SubmitFile` через same-origin REST с session/CSRF.
   Лишь серверный receipt подтверждает приём, а не успешную проверку. Ответы/статусы не оптимистические.
5. Открыть файл в списке: статус, попытки, версия, безопасный код ошибки, ID/hash и история.
   Активные задания перечитываются каждые 5 секунд, когда вкладка активна и есть связь;
   есть ручное обновление. Скрытая вкладка браузера не требует фонового polling.
6. Для `ready` прочитать extraction, проверить hash, parser/scan/signature versions и даты.
   Это недоверенный текст, не HTML/Markdown-команды. ID файла и SHA-256 текста можно выделить
   и скопировать в чат для отдельного решения Owner. Автокопирования в clipboard нет.
7. Отмена запрашивает точную показанную версию queued/processing job. Сервер подтверждает новую
   версию. Отмена не удаляет оригинал, не освобождает квоту и не обязана убить уже запущенный процесс.

Дизайн продолжает существующую редакционную панель: форма, читаемый список и инспектор ниже него,
один основной зелёный action, перенос длинных hash/имён на мобильных экранах. Нет отдельного сайта,
нового сервиса, декоративного dashboard или зависимости от установки проекта на ПК сотрудника.
Клавиатура использует нативные select/file picker/buttons/details; `prefers-reduced-motion` сохранён.

## Повторы и потерянные ответы

Upload key — `browser-file-v1:` + SHA-256 UTF-8 JSON-массива:
`["browser-file-v1", workspace_id, brand_id, filename, format, content_hash]`.
Все элементы — строки; format — `pdf` или `docx`. Пробелы/порядок не меняются произвольно.
Этот ключ не является секретом, средством авторизации или заменой server-side fingerprint.
Сервер дополнительно ограничивает ключ личным actor/workspace.

- Те же байты, имя, формат, workspace и бренд дают тот же ключ после повторного выбора,
  перезагрузки страницы или перехода на другую машину **под той же identity**. Менять ключ
  только ради сетевого повтора нельзя. Под другой учётной записью загрузка — отдельная запись.
- Пока форма открыта, при сетевой/неопределённой ошибке сохраняется только pending key,
  и отправка изменённого payload блокируется до сверки исходного запроса. Для исправления
  подтверждённой ошибки 4xx или `binary_ingestion_disabled` pending key освобождается.
- После перезагрузки клиент не помнит поля прежней формы: человек должен выбрать тот же файл,
  имя и бренд. Клиент не обещает межмашинную дедупликацию переименованных/изменённых документов.
- Намеренная повторная проверка оригинала — отдельный `knowledge_file_rescan` через чат,
  с новым idempotency key, новым scan/job и расходом обычной квоты. Повторная загрузка того же
  файла специально возвращает старую запись, даже если её состояние failed/cancelled/ready.
- Отмена использует `browser-file-cancel-v1:{file_id}:{expected_version}` и сохраняет точное тело
  при неопределённом ответе в открытом инспекторе. «Повторить отмену» повторяет его, даже если
  чтение показало другую версию. Подтверждённый конфликт требует перечитать состояние и явно
  решить, отменять ли новую версию. Чтения/поллинг никогда не запускают новые изменения.

Закрытие вкладки/смена workspace прерывает клиентский HTTP-запрос, **не** отменяет уже принятый
сервером job. Увидеть результат можно в списке или повторив исходную загрузку; подтверждённая
отмена выполняется только специальной командой, не через `AbortController`.

## Данные, права и границы

- Файл выбирает человек. Вкладка не читает произвольные пути и не получает автоматического
  доступа к вложениям Codex. Python/CLI, SSH/DB/API credentials и browser extensions не нужны.
- Owner видит разрешённые файлы workspace; Editor/Strategist — только свои. Viewer/Admin
  без `knowledge.write` не видят вкладку. Серверные permissions/RLS обязательны независимо от UI.
- Query keys включают workspace. Сессия/права/workspace управляются прежним private cache gate.
  Unmount aborts requests; detail/extraction/history queries имеют `gcTime: 0`. Поздний ответ
  загрузки после перехода не открывает файл в новом пространстве.
- File/base64 не попадают в TanStack mutation cache, localStorage, IndexedDB, service worker,
  логи или Git. Байты живут в выбранном File/краткоживущем запросе; успешный receipt очищает
  input. Это ограничение приложения, не гарантия стирания RAM/OS swap/истории браузера.
- Original любого формата не встраивается в iframe/object, не открывается inline. Извлечённый текст
  выводится React text nodes в `pre`, без `innerHTML`. Нет внешнего preview/telemetry сервиса.
- Браузер не активирует ingestion flags. `SMM_KNOWLEDGE_FILES_ENABLED=false` остаётся default;
  ожидаемый ответ объясняет, что необходим commissioning сканера и worker.
- Все прежние лимиты и проверки [binary pipeline](knowledge-files.md) и [ingestion jobs](ingestion-jobs.md)
  сохраняются: no OCR, свежие сигнатуры, sandbox, 200 файлов/100 МиБ lifetime quota, private originals.
  Старые сигнатуры видны в истории; возможность импорта по свежести решает сервер, не UI.
- Нет новых retry/rescan/import/activate кнопок. Эти действия доступны через существующие
  типизированные команды чата/API. Нет автоматической отправки документов модели или публикации.

## Проверка и ввод в эксплуатацию

Автотесты клиента: точные PDF/DOCX hash/base64, граница 2 МиБ, invalid size/name/magic,
стабильный ключ и различия metadata, формы/ошибки, потеря ответа, смена workspace/late reply,
извлечение как инертный текст, отмена/конфликт, pagination без случайного submit,
same-origin session/CSRF, 401/403 и abort signal. Обычные server/DB/REST/MCP тесты остаются обязательными.
Браузерный проход — только синтетические данные: desktop/mobile, file picker, upload/replay,
история/preview, клавиатура, отсутствие горизонтальной прокрутки; никаких реальных документов.

Локальная проверка этого среза: `pnpm check`, `pnpm test`, `pnpm build:web` — успешно;
213 Python-тестов, 2 Linux-only skip на Windows, 29 frontend unit/component/transport-тестов.
Существующие `content`, `knowledge`, `workspace` Playwright suites: 44/44 в Edge с двумя workers
на локальном Vite и mock API; это не проверка реального входа или сервера. При первом прогоне
с восемью workers существующий тест комментариев дал timeout; отдельно прошёл 3/3, затем весь
набор 44/44. Тест не отключён/не изменён; причина таймаута в этом срезе не установлена.
Новый файловый сценарий дополнительно пройден в Playwright CLI на 1280 и 393 px: нативный выбор
файла, потеря ответа и точный replay, отмена, offline, текстовый preview, отсутствие исполнения
script и горизонтальной прокрутки. Результаты синтетического UI smoke не являются ClamAV verdict.

После отдельного разрешения rollout:

1. Проверить private HTTPS/Tailscale и личный authentik/OIDC вход, применённую схему 0009
   и совместимые API/worker; никогда не копировать старые общие cookies между машинами.
2. Выполнить scanner/signatures/sandbox/RAM/disk/backup media+DB gates по `knowledge-files.md`.
   Только после этого включать ingestion/worker согласно runbook, не из браузера.
3. Развернуть согласованный build; сотруднику открыть ссылку, без копирования папки проекта.
4. С разрешённым тестовым документом сверить receipt/state/history в браузере и MCP на второй
   машине; проверить ту же identity, другую identity, чужой workspace, отзыв доступа и lost reply.
5. Отдельно разрешить реальный корпус, проверить extraction и выполнить точные Owner import/
   index activation/evaluation. Клиентский smoke этого не заменяет и не закрывает фазу 7.

Этот commit не требует новой migration. Откат frontend к предыдущей согласованной сборке скрывает
вкладку, но не отменяет jobs и не удаляет сохранённые документы. Deploy не следует автоматически из push.
